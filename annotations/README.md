[Steps](../docs/terminology.md#8-the-pipeline) read these files; no step writes here, with two narrow exceptions: step 070 may add rows at the end of `component_class_mapping.csv` and `held_out_looks.csv`, never changing or deleting a row already there. ## Annotating ground truth: the annotation tool

After running [step](../docs/terminology.md#8-the-pipeline) 050, from the repository folder:

```
py helpers/annotate.py
```

It opens the tool's home page in your browser (Ctrl+C in the terminal stops it), at http://127.0.0.1:8050/. Its two options: `--port N` serves it at port N instead of 8050, and `--no-browser` doesn't open the browser (open the address it prints yourself). Every view has a **Help** menu: **How to use this view** shows this file's section about it, and **The terms** shows `docs/terminology.md`. In Ground truth it also holds **Guidelines**, the [annotation guidelines](../docs/terminology.md#4-ground-truth-and-samples) ([`guidelines.md`](guidelines.md)): what to write in the [ground truth](../docs/terminology.md#4-ground-truth-and-samples), such as no [ground truth triple](../docs/terminology.md#4-ground-truth-and-samples) for a negated or uncertain fact. Read them before your first record. In every document the Help menu opens, a term with a dotted underline shows its definition when you hover over it (from `docs/terminology.md`), and a link opens its document in the same window. The tool runs only on your computer: no internet, no [model calls](../docs/terminology.md#8-the-pipeline), nothing to install. Everything it can and can't do is listed below, in *What the tool can do* and *What the tool can't do* (also at the end of **How to use this view** in Ground truth).

1. **Pick the batch** in the **Ground truth** dropdown at the top of the page, or press **Go on with batch N** on the home page (the first batch with records left to finish). The first time you open a [drafted batch](../docs/terminology.md#4-ground-truth-and-samples), the tool copies it into `ground_truth/`, renamed by its batch number (`outputs/intermediate_results/050_annotate/drafted_triples_batch1.csv` → `annotations/ground_truth/batch_001.csv`). From then on you're editing that copy; the drafted batch's own file in `outputs/` is never changed.
2. **Correct each [record](../docs/terminology.md#1-records-and-their-text)**: **About this record**, in its strip, shows its [pool](../docs/terminology.md#4-ground-truth-and-samples) position, its part (**tuning** or **held-out**), its maintainer, and its id, with two links under it: **Saved copy (harvest of …) ↗**, the record exactly as step 010 saved it from the catalog, on this computer (*Saved copy: not on this computer* instead, without a link, if the harvest's files aren't there), and **Web page in the catalog (live) ↗**, the record's page on data.nasa.gov, which may not work if the entry has since been removed or moved (a [component class](../docs/terminology.md#3-schemas) you learn from a [held-out record](../docs/terminology.md#7-evaluating-extraction-step-070) must not go into `schema_additions.txt`). Read its [text](../docs/terminology.md#1-records-and-their-text) first (the [source text](../docs/terminology.md#1-records-and-their-text) of each ground truth triple is highlighted in it; the one you're on is darker; a passage that several ground truth triples share is underlined, and each click on it goes to the next of them), then fix, delete (🗑) or add (+) ground truth triples. The [entity class](../docs/terminology.md#3-schemas) and predicate fields suggest the component classes of the [ground truth schema](../docs/terminology.md#3-schemas) as you type (the ground truth [schema](../docs/terminology.md#3-schemas)'s, plus any already [coined](../docs/terminology.md#3-schemas) in the ground truth); you can still type a new one. Under each of these fields, and under the [describes triple](../docs/terminology.md#2-triples)'s [object class](../docs/terminology.md#2-triples) (the [describes class](../docs/terminology.md#2-triples)), the component class's definition in the ground truth schema is shown, updated as you type, or *Not in the ground truth schema yet.* for one it lacks. An entity class or predicate not in the ground truth schema is an error (✖; it could be a typo), and step 070 won't evaluate a [finished record](../docs/terminology.md#4-ground-truth-and-samples) that uses one. If it's a typo, fix it; if it's new, press **Add … to the ground truth schema** under the ✖, type a one-line definition and press **Add**. A [pattern](../docs/terminology.md#3-schemas) used for the first time (a predicate between two entity classes no other ground truth triple joins) is flagged ⚑, for a look: a wrong entity class or direction shows this way. If it's right, there's nothing to do: the ground truth schema's patterns include every one the ground truth uses. To see a component class's other patterns, use **Patterns:** under the ground truth triple: one button for each of its [subject class](../docs/terminology.md#2-triples), predicate, and object class, each listing the ground truth schema's patterns with that component class in the same place, this triple's own in bold (from the saved ground truth, so they change once an edit is saved; a button is greyed out while its field is empty). A ground truth triple that no chain of the record's ground truth triples links to the catalog entry (the describes triple and the title) is flagged ⚑ too: look for the fact that connects it, and add it only if the record states it. **Help → Ground truth schema** lists, from every batch, the coined component classes, with the same buttons. The tool adds only that entry to `ground_truth_schema.txt`, checks nothing else in it changed (otherwise it puts the file back and says so), and gives each component class a `source:` line naming the ground truth records that use it, by part (`source: ground truth tuning #3; held-out #8`). To set a source text, select the passage in the text and press **Use selection**. The record's strip shows its place in the batch and what is left to fix (✖) or look at (⚑) in it, and the top of the list of records shows how many are finished; the ← and → keys go to the previous and next record when you aren't typing in a field. Every change is saved to the file at once, and the checks under each ground truth triple update as you go (✖ must be fixed, ⚑ worth a look).
3. **Tick "All [facts](../docs/terminology.md#2-triples) extracted"** on a record once every fact its text states is there. That sets `all_facts_extracted` to `1` on all its rows; untick it for a record you haven't finished.
4. **Commit** the file to Git, so the work is safe.

The tool also opens the files already in `ground_truth/`, like `batch_000.csv`. The first time it saves a file, it rewrites it in its own plain format: the same rows and values, but the CSV quoting may change, so Git can show more lines changed than you edited. Deleting every ground truth triple of a record keeps one row of the file holding only its id, which means "annotated, states no facts". The drafted batch's `flags` column isn't kept, since the tool recomputes the checks.

**Without the tool**, the same result by hand: copy the drafted batch into `ground_truth/` under its new name, correct it in any editor (the `flags` column can stay; it's ignored), set `all_facts_extracted` to `1` on every row of each finished record, and commit. Never correct the file in `outputs/`: it can be deleted and rebuilt, and your corrections would go with it.

### Checking the translation table

Step 070 compares extraction, whose [extracted triples](../docs/terminology.md#6-extracting-with-a-schema-step-060) use the [current schema](../docs/terminology.md#6-extracting-with-a-schema-step-060)'s [entity classes](../docs/terminology.md#3-schemas) and predicates, with your [ground truth](../docs/terminology.md#4-ground-truth-and-samples), which uses the [ground truth schema](../docs/terminology.md#3-schemas); this table says which [component class](../docs/terminology.md#3-schemas) of the current schema means which of the ground truth schema. It needs checking only when step 070 stops and asks for the rows it added to be checked.

Choose **[Translation table](../docs/terminology.md#7-evaluating-extraction-step-070)** at the top of the page. It shows `component_class_mapping.csv` one row per component class of the current schema (the one [step](../docs/terminology.md#8-the-pipeline) 060 used last), and opens on the rows still to check (untick *Show only rows to check* to see them all). Rows only past [schemas](../docs/terminology.md#3-schemas) use are hidden (tick *Show the … row(s) for component classes only past schemas used* to see them): they are kept so that a component class that comes back in a later schema needn't be checked again. Each row shows (every note a row can show, and what step 070 does about it: *row state* in the terminology):

- the component class and its definition in the current schema;
- **Means, in the ground truth schema**: a list of the ground truth schema's component classes (and `(none)`), with the chosen one's definition below it: only those in `ground_truth_schema.txt`, as step 070 reads it, so a coined one isn't offered (add it to the ground truth schema first; saving a row that names one is refused, and says so);
- for a [predicate](../docs/terminology.md#3-schemas), **Swap [subject](../docs/terminology.md#2-triples) and [object](../docs/terminology.md#2-triples)**, with an example: the first extracted triple with that predicate and its [translated extracted triple](../docs/terminology.md#7-evaluating-extraction-step-070) (`Aqua CARRIES MODIS --> MODIS ABOARD Aqua`), so you can read whether it says the same thing;
- **⚑ [suggested](../docs/terminology.md#7-evaluating-extraction-step-070)**: pick the suggested component class if right (e.g. `Gadget` --> `Device`).
- **⚑ [now exists](../docs/terminology.md#7-evaluating-extraction-step-070)**: probably out of date: change it, unless the ground truth's component class means something else.
- **⚑ [shared](../docs/terminology.md#7-evaluating-extraction-step-070)**: fine if your ground truth doesn't make that distinction.
- **✖ [missing target](../docs/terminology.md#7-evaluating-extraction-step-070)**: the row translates to a component class the ground truth schema doesn't have (the list shows it marked ⚠): pick another, or `(none)`, or add it to the ground truth schema. Saving leaves such a row as it is until you change it.
- **Checked**: tick it once the translation is right; that also stores the current schema's definition of the component class in the row. A row whose two component classes are spelled the same was accepted automatically and says so: it needs nothing, unless the two definitions shown mean different things. Then pick the right counterpart; the row becomes an ordinary one to check, and **Checked** appears.
- **⚑ [stale](../docs/terminology.md#7-evaluating-extraction-step-070)**: the current schema's definition of the component class, or the ground truth schema's definition of the component class it translates to, has changed since the row was checked; it shows the old definition; tick **Checked** again once you've confirmed (or fixed) the translation (a row accepted automatically gets a **Checked** box too while it is stale).

Every change is saved to `component_class_mapping.csv` at once. The tool can't add or reorder rows (step 070 adds them), and the only rows it can delete are repeats: one component class, one row, so if a hand edit left two rows for the same component class, the page says so and shows a **Delete this row** button on each (keep the right one, usually the one whose stored definition matches the current schema's). If step 070 adds rows while the page is open, a save keeps them. A save is refused, and nothing is saved, in two cases, checked in this order: the rows on the page no longer match the file (the page asks you to reload); or a row names, in *Means, in the ground truth schema*, a component class the ground truth schema doesn't have, which you chose (a coined one: add it to the ground truth schema first; any other: pick one from the list, or `(none)`). A row whose missing target you left as it was is saved unchanged, and stays marked.

### Reviewing partial pairs

After a run of step 070, this view is where to decide, for pairs whose [subject instances](../docs/terminology.md#2-triples) or [object instances](../docs/terminology.md#2-triples) agree only partly ("MODIS" and "MODIS Terra"), whether they state the same fact. 070's report says when some are waiting; only [tuning records](../docs/terminology.md#7-evaluating-extraction-step-070) are shown.

Choose **[Partial pairs](../070_evaluate/metrics/pairs.md)** at the top of the page, after a [run](../docs/terminology.md#8-the-pipeline) of [step](../docs/terminology.md#8-the-pipeline) 070. A [partial pair](../070_evaluate/metrics/pairs.md)'s subject instances or object instances agree only partly (exactly when: [`070_evaluate/metrics/pairs.md`](../070_evaluate/metrics/pairs.md)): `MODIS` and `Moderate Resolution Imaging Spectroradiometer (MODIS)`, but also `MODIS` and `MODIS Terra`, a different instrument. Each partial pair is a box: the [record](../docs/terminology.md#1-records-and-their-text) on top, then the [ground truth triple](../docs/terminology.md#4-ground-truth-and-samples) ([ground truth schema](../docs/terminology.md#3-schemas)) and the [translated extracted triple](../docs/terminology.md#7-evaluating-extraction-step-070) side by side; click *The record's [text](../docs/terminology.md#1-records-and-their-text)* under them to read the record's text, and decide from it, not from how alike the two look. A subject instance, predicate or object instance that differs between the two triples, once [evened out](../docs/terminology.md#2-triples), is filled in color on both sides, and the words only one of them has are darker. Press **Same [fact](../docs/terminology.md#2-triples)** or **[Not the same fact](../docs/terminology.md#7-evaluating-extraction-step-070)**; **Take back** removes a [verdict](../docs/terminology.md#7-evaluating-extraction-step-070). **Same fact**: the pairing doesn't change, and the pair counts as reviewed. **Not the same fact**: step 070 won't pair the two in its next run and every later one, unless you change your verdict; it looks for another partner for each, and one left without a partner counts as extracted only (the occurrence) or ground truth only (the ground truth triple). A verdict is filed under the record and both triples' subject instance, predicate and object instance, evened out, so it stops applying if the [translation table](../docs/terminology.md#7-evaluating-extraction-step-070) changes the translated [extracted triple](../docs/terminology.md#6-extracting-with-a-schema-step-060). When the pair's translated extracted triple occurs more than once in the record (its [multiplicity](../070_evaluate/metrics/pairs.md#example) is above 1), a ⚑ pill says how many times; click it to list its occurrences, each as the extracted triple ([current schema](../docs/terminology.md#6-extracting-with-a-schema-step-060)) that translates to it, with what step 070 made of it: the occurrence in this pair, extracted only, or paired with another ground truth triple. Only one occurrence can pair with the ground truth triple. Every verdict is saved to `partial_pair_reviews.csv` at once; rerun step 070 to see its effect. Only tuning records are shown (until the final evaluation): reviewing held-out pairs would mean looking at held-out results.

### Adding to the schema additions

This optional view adds [entity classes](../docs/terminology.md#3-schemas), predicates, or patterns to the [current schema](../docs/terminology.md#6-extracting-with-a-schema-step-060) by hand (the [schema additions](../docs/terminology.md#3-schemas)), e.g. on a mentor's advice, from outside knowledge, or from [tuning records](../docs/terminology.md#7-evaluating-extraction-step-070) only.

Choose **Schema additions** at the top of the page. It lists the entries of `schema_additions.txt` (*Edit*, *Delete*) and opens a form with **+ Add an entry**: the entry type, then for an entity class or a [predicate](../docs/terminology.md#3-schemas) the [component class](../docs/terminology.md#3-schemas) (one word: entity classes in CamelCase, predicates in UPPER_SNAKE_CASE), a one-line definition, and, for a predicate, its [patterns](../docs/terminology.md#3-schemas) (`Subject -> Object; …`); for a pattern, its [subject class](../docs/terminology.md#2-triples), predicate, and [object class](../docs/terminology.md#2-triples) (e.g. a new pattern for a predicate the [schema](../docs/terminology.md#3-schemas) already has); and the source. What's wrong is shown as you type, and the tool won't save an entry that is wrong; it names the first problem, checking in this order: a pattern without a subject class, a predicate, and an object class, one word each; an entry type other than entity class, predicate, or pattern; a component class that isn't one word (letters or digits, no spaces, no `;`, no `->`); an entity class or predicate without a definition; no source; a source naming the [ground truth](../docs/terminology.md#4-ground-truth-and-samples) that names no [record](../docs/terminology.md#1-records-and-their-text), names a [held-out record](../docs/terminology.md#7-evaluating-extraction-step-070), doesn't say `tuning`, or names a number that isn't a [pool position](../docs/terminology.md#4-ground-truth-and-samples) (checked in that order: `source: ground truth tuning #12, #15`; the same check [step](../docs/terminology.md#8-the-pipeline) 060 makes); for a predicate, a pattern that isn't two entity classes, one word each (`Subject -> Object`). The comments at the top of the file are kept.

A shortcut:

- **Component classes outside the schema:** below the entries, each entity class or predicate that step 060's last [run](../docs/terminology.md#8-the-pipeline) used though the current schema doesn't have it (so 060 removed those [classed triples](../docs/terminology.md#2-triples); held-out records never counted), each with *Add*, which fills in the entry type, the component class, and the source. You write the definition, and the next run of 060 can use it. Patterns aren't listed: 060 keeps an [extracted triple](../docs/terminology.md#6-extracting-with-a-schema-step-060) whose pattern the schema lacks, and only flags it.

### The ground truth schema

This view gives an [entity class](../docs/terminology.md#3-schemas) or predicate of the [ground truth schema](../docs/terminology.md#3-schemas) a definition, renames it, or merges two that mean the same thing, in every file at once. Use it when a [component class](../docs/terminology.md#3-schemas) you coined needs a definition or renaming.

**Help → Ground truth schema** (in [Ground truth](../docs/terminology.md#4-ground-truth-and-samples) and in the translation table) opens the ground truth schema at a glance, over the view you're on: entity classes and predicates side by side, each with its definition and its uses (a predicate also with its patterns, the file's and those the ground truth uses), and a box to filter them. **Edit definitions, rename, or merge…** there opens this view. It lists every entity class and [predicate](../docs/terminology.md#3-schemas) of the ground truth schema, and any [coined](../docs/terminology.md#3-schemas) in the ground truth that it doesn't have yet. Each shows its definition, how many ground truth triples use it and in which files, and which component classes of the current or a [past schema](../docs/terminology.md#6-extracting-with-a-schema-step-060) the [translation table](../docs/terminology.md#7-evaluating-extraction-step-070) translates to it. For each one:

- **Save definition** changes its definition in the ground truth schema (only that line of the file changes). The translation table's rows that translate to it become stale: check them again (*Translation table*). For a coined component class, the button is **Add to the ground truth schema** instead.
- **[Rename or merge…](../docs/terminology.md#3-schemas)**: type the new component class and press the button. If the one you type is, by [loose match](../docs/terminology.md#3-schemas), another entity class or predicate of the ground truth schema or one coined in the ground truth, the two are merged into it; any other spelling renames it, and one that differs from the old one only in capitals or punctuation respells it (a rename). The tool refuses, naming the first that applies, in this order: the old one is neither in the ground truth schema nor coined (the page is out of date: reload it); the old or the new one is `CatalogEntry`, `DESCRIBES`, or `X` (written by code); the new one is spelled exactly as the old; the new one isn't one word (letters or digits, no spaces, no `;`, no `->`, not starting with `#`); a merge would leave two of your [partial pair reviews](../docs/terminology.md#7-evaluating-extraction-step-070) on the same pair with different verdicts (take one back first); nothing uses the old one. Before anything changes, the page shows every file it would change, and what in it, with notes (e.g. translation table rows that will then be stale, or [drafted batches](../docs/terminology.md#4-ground-truth-and-samples) not opened yet that still use the old component class). **Make these changes** applies every change listed; **Cancel** leaves everything as it was. The change is made in every file at once, or in none: if writing one file fails, the files already written are put back.

What a rename or merge changes:

1. every `annotations/ground_truth/batch_*.csv`: each `subject_class` and `object_class` (for an entity class), or each `predicate` (for a predicate), holding it in any spelling (by loose match);
2. `ground_truth_schema.txt`: renaming renames its entry; merging deletes its entry (with its definition and `source:` line) and, for a predicate, moves its patterns under the one it's merged into; every pattern naming it names the new one;
3. `component_class_mapping.csv`: each row translating to it translates to the new one (a merged row becomes stale when the new one's definition differs from the one it was checked against);
4. for a predicate, `partial_pair_reviews.csv`: your verdicts are filed under the predicate's spelling, so they're changed too and still apply. If a merge would make two [partial pairs](../070_evaluate/metrics/pairs.md) the same pair, with different verdicts, nothing changes and the page says so: take one back first (*Partial pairs*).

It never changes the drafted batches in `outputs/` (step 050's output), and never `CatalogEntry`, `DESCRIBES`, or `X`, which code writes. Commit the changed files afterwards.

This view shows, read-only, what subject-matter experts wrote on the review page about the [ground truth schema](../docs/terminology.md#3-schemas) and the [translation table](../docs/terminology.md#7-evaluating-extraction-step-070): the comment files and emails in `annotations/reviews/`, read by the same code as `py helpers/review_page.py --read` ([helpers/review_page.md](../helpers/review_page.md)).

### Renaming or merging a component class of the ground truth schema

The tool does this: *The ground truth schema*, above. Without the tool, by hand, for a [component class](../docs/terminology.md#3-schemas) `Old` that should be called `New` (renaming), or that means the same as `New`, which already exists (merging):

1. **The [ground truth](../docs/terminology.md#4-ground-truth-and-samples) files.** In every `annotations/ground_truth/batch_*.csv`, change `Old` to `New` wherever it appears: in `subject_class` and `object_class` for an [entity class](../docs/terminology.md#3-schemas), in `predicate` for a predicate. A file you miss keeps `Old` in the ground truth, where it is then a coined component class, and its [ground truth triples](../docs/terminology.md#4-ground-truth-and-samples) no longer match what the [translation table](../docs/terminology.md#7-evaluating-extraction-step-070) translates to.
2. **The [ground truth schema](../docs/terminology.md#3-schemas)** (`annotations/ground_truth_schema.txt`). Renaming: change the entry's component class, and `Old` in its patterns. Merging: delete `Old`'s entry, and move its patterns under `New`.
3. **The translation table** (`annotations/component_class_mapping.csv`). In every row whose `component_class_in_gtt` is `Old`, write `New`. Step 070 stops on a row naming a component class that's no longer in the ground truth schema, so a row you miss is caught. When merging, a changed row is then stale if `New`'s definition differs from `Old`'s: check it again (*Translation table*).
4. **For a predicate only:** your [partial pair reviews](../docs/terminology.md#7-evaluating-extraction-step-070) are filed under the predicate's spelling, so the [partial pairs](../070_evaluate/metrics/pairs.md) with `Old` come back as not reviewed: review them again (*Partial pairs*).
5. Run step 070 again, and commit the changed files.

Example: *Suppose:* while annotating, you coined `Satelite` (a misspelling) in two ground truth triples, and added it to the ground truth schema as "a craft in orbit". Step 070 then wrote the translation table row `Satellite` ([current schema](../docs/terminology.md#6-extracting-with-a-schema-step-060)) → `Satelite` (ground truth schema), which you checked. The ground truth schema also has `Spacecraft`, "a craft that operates in space", which means the same. *Then,* to merge `Satelite` into `Spacecraft`: (1) in both ground truth triples, change `Satelite` to `Spacecraft`; (2) delete the `Satelite` entry from the ground truth schema; (3) in that translation table row, change `Satelite` to `Spacecraft`. The row is then stale, since the definition it stored ("a craft in orbit") isn't `Spacecraft`'s: check it again.

## The ground truth files

The [ground truth](../docs/terminology.md#4-ground-truth-and-samples) is every `batch_*.csv` file in `ground_truth/`, taken together. `batch_000.csv` holds the [records](../docs/terminology.md#1-records-and-their-text) annotated before the pipeline existed ([pool](../docs/terminology.md#4-ground-truth-and-samples) positions 0–5, 2026-09); `batch_001.csv`, `batch_002.csv`, … are each corrected from [step](../docs/terminology.md#8-the-pipeline) 050's [drafted batch](../docs/terminology.md#4-ground-truth-and-samples) of the same number.

Their columns:

`id, subject, subject_class, predicate, object, object_class, source_text, all_facts_extracted` (a drafted batch's `flags` column may stay), and `drafted_by`: the model that drafted the classed triple (step 050 writes it; the [annotation tool](../docs/terminology.md#4-ground-truth-and-samples) keeps it, and leaves it empty on a row you add). `batch_000.csv`, annotated before the pipeline, has it too: it names the model on the rows a model drafted (some rows of [pool positions](../docs/terminology.md#4-ground-truth-and-samples) 1, 2, 3, and 4) and is empty on the rest. Step 060 reads it to warn when it would extract with the model that drafted the ground truth, or one from the same maker. One row per [classed triple](../docs/terminology.md#2-triples), grouped by record. A row with an `id` but an empty subject, [predicate](../docs/terminology.md#3-schemas), and object says "this record was annotated and states no [facts](../docs/terminology.md#2-triples)".

### What the pipeline checks

Every [step](../docs/terminology.md#8-the-pipeline) that reads `ground_truth/` (040, 050, 060, and 070, through `common/common_helpers/ground_truth.py`) lists the [ground truth](../docs/terminology.md#4-ground-truth-and-samples)'s own problems in its [report](../docs/terminology.md#8-the-pipeline)'s warnings, and the [annotation tool](../docs/terminology.md#4-ground-truth-and-samples) shows them on its page; none is ever silently fixed. All six, each with what it means and what to do, and which steps show them before paying: [`docs/running_on_nasa_laptop.md`](../docs/running_on_nasa_laptop.md), section 7, the rows starting *Ground truth,*. Of them, only [the same classed triple twice](../docs/terminology.md#4-ground-truth-and-samples) in one record stops a step (070, until you delete one of the two rows).
