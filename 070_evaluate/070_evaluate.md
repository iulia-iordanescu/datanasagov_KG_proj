# 070_evaluate

Terms ([precision](../docs/terminology.md#7-evaluating-extraction-step-070), [recall](../docs/terminology.md#7-evaluating-extraction-step-070), [pair](../docs/terminology.md#7-evaluating-extraction-step-070), pairing, [margin of error](../docs/terminology.md#7-evaluating-extraction-step-070), [bootstrap](../docs/terminology.md#7-evaluating-extraction-step-070), [tuning part](../docs/terminology.md#7-evaluating-extraction-step-070), [held-out part](../docs/terminology.md#7-evaluating-extraction-step-070), …) are as defined in [docs/terminology.md](../docs/terminology.md), especially section *Evaluating extraction (step 070)*.

## Purpose

Evaluates what [step](../docs/terminology.md#8-the-pipeline) 060 extracted against the [ground truth](../docs/terminology.md#4-ground-truth-and-samples), the answer key:

- **[precision](../docs/terminology.md#7-evaluating-extraction-step-070)**: when 060 says something, how often it is right;
- **[recall](../docs/terminology.md#7-evaluating-extraction-step-070)**: of the ground truth triples, how many 060 found;

each with its **[margin of error](../docs/terminology.md#7-evaluating-extraction-step-070)**, so a real improvement can be told from luck. Around them:

- **[entity-class accuracy](../docs/terminology.md#7-evaluating-extraction-step-070)**: of the pairs, how often 060 also named the right [entity classes](../docs/terminology.md#3-schemas);
- **[F1](../docs/terminology.md#7-evaluating-extraction-step-070)**: precision and recall in one number, the usual headline for comparing [runs](../docs/terminology.md#8-the-pipeline) or [models](../docs/terminology.md#8-the-pipeline);
- **[recall upper bound](../docs/terminology.md#7-evaluating-extraction-step-070)**: how much of the ground truth the [schema](../docs/terminology.md#3-schemas) can express at all (the most recall can be), and **recall [within reach](../docs/terminology.md#7-evaluating-extraction-step-070)**: how well 060 did on what it could do; each also in a strict version, with the entity classes. A low upper bound means the schema needs work; a high upper bound with low [recall within reach](metrics/recall_within_reach.md) means the extraction does;
- **[describes accuracy](../docs/terminology.md#7-evaluating-extraction-step-070)**: how often 060 named the right describes class, next to what always naming the most common [describes class](../docs/terminology.md#2-triples) would get.

Before comparing, the [component classes](../docs/terminology.md#3-schemas) of the [current schema](../docs/terminology.md#6-extracting-with-a-schema-step-060) (the one 060 used) are translated into the [ground truth schema](../docs/terminology.md#3-schemas), through the [translation table](../docs/terminology.md#7-evaluating-extraction-step-070), which you check. Only the **[fair sample](../docs/terminology.md#4-ground-truth-and-samples)** of the ground truth is evaluated, and by default only its **[tuning part](../docs/terminology.md#7-evaluating-extraction-step-070)**: the [held-out part](../docs/terminology.md#7-evaluating-extraction-step-070) is kept for the end.

The ground truth was drafted by a model (050) and corrected by a person, not written from scratch; so recall is likely overstated (see [`metrics/recall.md`](metrics/recall.md), *Assumes and can't see*). The [report](../docs/terminology.md#8-the-pipeline) says so, under *Where these numbers come from*.

## To do

What to do, and when, is in [`docs/upkeep.md`](../docs/upkeep.md), one page for every step; `py run_pipeline.py --status` (or the [annotation tool](../docs/terminology.md#4-ground-truth-and-samples)'s home page) lists what is waiting now. For this step, in short:

- When it stops: add the [entity classes](../docs/terminology.md#3-schemas) and predicates the [finished records](../docs/terminology.md#4-ground-truth-and-samples) coined to the [ground truth schema](../docs/terminology.md#3-schemas), and check the [translation table](../docs/terminology.md#7-evaluating-extraction-step-070)'s rows ([*When step 070 stops*](../docs/upkeep.md#when-step-070-stops)).
- After it runs: review the [partial pairs](metrics/pairs.md), then run it again; read the report's *Component class mismatches* and `per_record.md` ([*After step 070*](../docs/upkeep.md#after-step-070)).
- Look at the [held-out part](../docs/terminology.md#7-evaluating-extraction-step-070) only at the end ([*At the end: the held-out part*](../docs/upkeep.md#at-the-end-the-held-out-part)).

## How to run

From the repository folder, with the environment active (`docs/virtual_environment_setup.md`), and, when [component classes](../docs/terminology.md#3-schemas) need translating, on a computer that can reach the model's service with its key in `.env` (`docs/running_on_nasa_laptop.md`):

```
py 070_evaluate/run.py --help                       every input and setting, with its default
py 070_evaluate/run.py                              the tuning part
py 070_evaluate/run.py --evaluate_held_out true     also the held-out part (for the end; each look is logged)
py 070_evaluate/run.py --confirm_paid_calls false   don't ask (unattended runs)
```

Needs 060's output. The first [run](../docs/terminology.md#8-the-pipeline) with a new [schema](../docs/terminology.md#3-schemas) stops after adding rows to `annotations/component_class_mapping.csv`: check them, then run again.

**Paying.** Before its first [model call](../docs/terminology.md#8-the-pipeline), 070 logs its plan (how many component classes to translate, the [model](../docs/terminology.md#8-the-pipeline)) and waits: Enter starts, anything else stops the run having spent nothing. Any warnings were already shown, and asked about, before evaluating (stage 1), so this question doesn't repeat them. Its first call is the [test call](../docs/terminology.md#8-the-pipeline), which checks that the model name and key work. A run whose answers are all in the cache never asks and never pays. Model calls, all about the [translation table](../docs/terminology.md#7-evaluating-extraction-step-070): one per 100 component classes of the [current schema](../docs/terminology.md#6-extracting-with-a-schema-step-060) without a row in `annotations/component_class_mapping.csv`, and at most one more when there are both `(none)` rows of the current schema and component classes of the [ground truth schema](../docs/terminology.md#3-schemas) nothing translates to (asked once for each such two lists). None otherwise: the evaluation is code.

**The cache.** Every model answer is kept in `cache/`, under a [fingerprint](../docs/terminology.md#8-the-pipeline) of everything that decided it: the model, the prompt's exact text, and what was sent. A rerun reuses every answer whose fingerprint is unchanged: a failed call isn't kept, so a rerun asks only the calls that failed; editing a prompt asks again exactly the calls that use it; deleting `cache/` (or all of `outputs/`) means paying for every call again.

## How it works

Four [stages](../docs/terminology.md#8-the-pipeline), in `070_evaluate/run.py`'s `main()`; stage 2 may ask the [model](../docs/terminology.md#8-the-pipeline) (for [component classes](../docs/terminology.md#3-schemas) without a row, and for suggestions on `(none)` rows), the others are code:

1. **Pick the [records](../docs/terminology.md#1-records-and-their-text)** (`records.py`, `pick_records`). A record is evaluated if you've finished it in the [ground truth](../docs/terminology.md#4-ground-truth-and-samples) and 060's last [run](../docs/terminology.md#8-the-pipeline) extracted it. Of those, only the **[fair sample](../docs/terminology.md#4-ground-truth-and-samples)**: the [pool](../docs/terminology.md#4-ground-truth-and-samples)'s first records, up to the first one not evaluated. A record after a gap (an unfinished or unextracted pool record before it) or outside the pool is left out and named, so every evaluated record belongs to a fair sample. Every warning found here (*Checks and warnings*: ground truth problems, records left out, …) is shown before anything is evaluated, and the run asks whether to go ahead (unless `confirm_paid_calls` is false); [the same classed triple twice](../docs/terminology.md#4-ground-truth-and-samples) in a record stops the run.
2. **Translate component classes** (`component_classes.py`, `translate_component_classes`), through `annotations/component_class_mapping.csv`:

   ```
   kind,component_class_from_past_or_crt_schema,component_class_in_gtt,swap_subject_and_object,checked,definition_from_past_or_crt_schema,definition_in_gtt
   entity class,Satellite,Spacecraft,no,yes,A craft that orbits a body.,A vehicle in space.
   predicate,CARRIES,ABOARD,yes,yes,Has on board.,Is carried on.     "A CARRIES B" is "B ABOARD A"
   entity class,Gadget,(none),no,yes,A small device.,                 nothing in the ground truth means this
   entity class,Dataset,Dataset,no,same component class,A set of data.,A set of observations.
   ```

   For each component class of the [current schema](../docs/terminology.md#6-extracting-with-a-schema-step-060) without a row: one equal to a component class of the [ground truth schema](../docs/terminology.md#3-schemas) (by [loose match](../docs/terminology.md#3-schemas)) gets a row at once, `checked` = `same component class` (you can still change it in the [annotation tool](../docs/terminology.md#4-ground-truth-and-samples), if the two definitions mean different things; it then needs checking like any other row); the model proposes the others (one [paid call](../docs/terminology.md#8-the-pipeline) per 100, after the usual confirmation), `checked` = `no`. The [step](../docs/terminology.md#8-the-pipeline) then stops. You check each `no` row: fix `component_class_in_gtt` (a component class of the ground truth schema, or `(none)`) and `swap_subject_and_object` where wrong, then set `checked` to `yes`. Evaluation runs only once every row it needs is checked. Each row also keeps two definitions from when it was written or last checked: the current schema's definition of its component class (`definition_from_past_or_crt_schema`), and the ground truth schema's definition of its component class of the ground truth schema (`definition_in_gtt`; empty for `(none)`). A row is **[stale](../docs/terminology.md#7-evaluating-extraction-step-070)** when either definition has changed since. A stale row stops the step until you check it again; checking it again stores both definitions as they are then. So the one table can serve every schema, and every version of the ground truth schema: a row stays checked while both meanings stay the same. The model's proposals are only a starting point: in testing, the [stand-in model](../docs/terminology.md#8-the-pipeline)'s deliberate mistake (`Phase` → `(none)` instead of `MissionPhase`) is exactly what the check is for.
3. **Compare, record by record** (`pairing.py`, `compare`). Each [extracted triple](../docs/terminology.md#6-extracting-with-a-schema-step-060) is translated into a [translated extracted triple](../docs/terminology.md#7-evaluating-extraction-step-070). Then the occurrences in the record's multiset of translated extracted triples and its ground truth triples are paired, [exact pairs](metrics/pairs.md) first, then [partial pairs](metrics/pairs.md), as [`metrics/pairs.md`](metrics/pairs.md) defines them. Every partial pair is listed in `per_record.md`, and you review the [tuning part](../docs/terminology.md#7-evaluating-extraction-step-070)'s partial pairs in `py helpers/annotate.py`, *Partial pairs*: an occurrence and a [ground truth triple](../docs/terminology.md#4-ground-truth-and-samples) you mark `not the same fact` are never paired.

   Which ground truth triples are [within reach](../docs/terminology.md#7-evaluating-extraction-step-070) or [within strict reach](../docs/terminology.md#7-evaluating-extraction-step-070): [`metrics/recall_upper_bound.md`](metrics/recall_upper_bound.md). The [describes triples](../docs/terminology.md#2-triples) are compared only on their [describes class](../docs/terminology.md#2-triples), apart from the other [classed triples](../docs/terminology.md#2-triples), since code writes the rest of them.
4. **Compute the metrics** (`stats.py`, `compute_metrics`). Precision, recall, F1, [entity-class accuracy](../docs/terminology.md#7-evaluating-extraction-step-070), the [recall upper bound](../docs/terminology.md#7-evaluating-extraction-step-070), [recall within reach](../docs/terminology.md#7-evaluating-extraction-step-070), and the [describes accuracy](metrics/describes.md), each in its versions: [`metrics.md`](metrics.md#the-metrics).

   Each is given at both [pair levels](metrics/pairs.md) (**exact**, and **partial**, which counts exact and partial pairs), with its **[margin of error](../docs/terminology.md#7-evaluating-extraction-step-070)** by the **[bootstrap](../docs/terminology.md#7-evaluating-extraction-step-070)** (below), for the tuning part, for the [held-out part](../docs/terminology.md#7-evaluating-extraction-step-070) when asked, and per [stratum](../docs/terminology.md#4-ground-truth-and-samples). The [report](../docs/terminology.md#8-the-pipeline) adds a table of each record's describes class, as extracted versus as in the ground truth.

**Then the results** (`results`): `metrics.json`, `per_record.md` and `compared_triples.csv` are written, replacing the last run's (whose versions are kept in `previous_runs/<run id>/` when they differ: `helpers/audit.md`, *Where to look*); with `--evaluate_held_out true`, a line is added to `annotations/held_out_looks.csv`; the report. The report also lists **[component class mismatches](../docs/terminology.md#7-evaluating-extraction-step-070)** (`pairing.py`, `component_class_mismatches`), possible translation errors, found in the [tuning records](../docs/terminology.md#7-evaluating-extraction-step-070)' classed triples only, also when the held-out part is shown (a row changed because of a [held-out record](../docs/terminology.md#7-evaluating-extraction-step-070) would let the held-out records influence the pipeline): a wrong or missing row of the [translation table](../docs/terminology.md#7-evaluating-extraction-step-070) leaves a trace where extraction found the fact but a component class differs. A pair whose [subject class](../docs/terminology.md#2-triples) or [object class](../docs/terminology.md#2-triples) differs suggests the row of the current schema's [entity class](../docs/terminology.md#3-schemas) is wrong (its row may say `(none)`, or the wrong entity class); an extracted only occurrence and a ground truth only triple with the same [subject instance](../docs/terminology.md#2-triples) and [object instance](../docs/terminology.md#2-triples) (or the two swapped) but different predicates suggest the predicate's row is wrong (or its `swap_subject_and_object`). Each mismatch is counted, e.g. *Gadget (current schema) --> (none), met Device (ground truth schema) 9 times*; a single one may just be extraction choosing the wrong component class, a frequent one is a row to check.

The code: `070_evaluate/` holds `run.py` (the [control panel](../docs/terminology.md#8-the-pipeline): inputs, [settings](../docs/terminology.md#8-the-pipeline), and the [moves](../docs/terminology.md#8-the-pipeline), in order); `070_evaluate/070_evaluate_helpers/` holds `moves.py` (the moves, and writing the results), `records.py`, `component_classes.py`, `pairing.py`, `stats.py` and `readings.py` (the metrics read as sentences); `070_evaluate/070_evaluate_prompts/` holds the prompts (see *Prompts*). Shared with other steps: `common/common_helpers/ground_truth.py` (reading the ground truth; the fair sample), `common/common_helpers/text_match.py`, `common/common_helpers/triples_io.py`, `common/common_helpers/files.py` (adding lines without changing any), `common/common_helpers/cache.py`, `common/common_helpers/llm.py`.

### Reading the metrics

A percentage alone is hard to use, so for each part the [report](../docs/terminology.md#8-the-pipeline) also writes every metric out as sentences, filled in with that [run](../docs/terminology.md#8-the-pipeline)'s own counts (section *Reading the metrics* of the report; code: `readings.py`). It starts with **where these numbers come from**: extraction's run and [model](../docs/terminology.md#8-the-pipeline), its [schema](../docs/terminology.md#3-schemas) and how many schema entries its [schema additions](../docs/terminology.md#3-schemas) had (naming any learned from tuning [records](../docs/terminology.md#1-records-and-their-text), which come from the very records being evaluated), the [translation table](../docs/terminology.md#7-evaluating-extraction-step-070), the [ground truth](../docs/terminology.md#4-ground-truth-and-samples) records ([pool](../docs/terminology.md#4-ground-truth-and-samples) positions), the partial [pairs](../docs/terminology.md#7-evaluating-extraction-step-070) reviewed or not, for the [held-out part](../docs/terminology.md#7-evaluating-extraction-step-070) how many times it has been looked at, and where each run's full recipe is (its report's Run, [Settings](../docs/terminology.md#8-the-pipeline), Prompts, and Inputs sections).

Then, per metric, the readings that hold for it, such as:

- the counts behind it, e.g. "of the 8 occurrences of these records (one per [extracted triple](../docs/terminology.md#6-extracting-with-a-schema-step-060), translated into the [ground truth schema](../docs/terminology.md#3-schemas)), 4 (50%) are correct at the exact level";
- read as a chance, e.g. "a [ground truth triple](../docs/terminology.md#4-ground-truth-and-samples) has a 50% chance of being found as an [exact pair](metrics/pairs.md)";
- what it means for a [knowledge graph](../docs/terminology.md#8-the-pipeline) built from the extracted triples, e.g. "approximately 50% of those edges would be correct at the exact level";
- how sure it is: "for the whole catalog, exact precision is likely between 52% and 70%" (the [margin of error](../docs/terminology.md#7-evaluating-extraction-step-070)), or, with fewer than 20 records, that it has none;
- what it assumes, e.g. that the ground truth lists every [fact](../docs/terminology.md#2-triples) the records state;
- where needed, what it can't see, e.g. [entity-class accuracy](../docs/terminology.md#7-evaluating-extraction-step-070) can't see mix-ups between [component classes](../docs/terminology.md#3-schemas) of the [current schema](../docs/terminology.md#6-extracting-with-a-schema-step-060) that translate to the same component class of the ground truth schema.

A metric gets only the readings that apply to it: the [recall upper bound](../docs/terminology.md#7-evaluating-extraction-step-070), for instance, has no "chance" reading, and *describes accuracy* is read against what always naming the most common [describes class](../docs/terminology.md#2-triples) would get.

### The margin of error, and the checks it needs

How it is computed, what it assumes, and how the [report](../docs/terminology.md#8-the-pipeline) checks each assumption: [`070_evaluate/metrics/approximately.md`, *Sampling error*](metrics/approximately.md#sampling-error).

**Per [stratum](../docs/terminology.md#4-ground-truth-and-samples)**, every stratum of the [pool](../docs/terminology.md#4-ground-truth-and-samples) is listed with its number of evaluated [records](../docs/terminology.md#1-records-and-their-text), its share of them, and its share of the pool; its numbers appear once it has 20 records. Overall numbers need no weighting, because each stratum had places in proportion to its size. Two more checks:

- the report warns when the evaluated records' mix of strata drifts from the pool's: [`metrics/approximately.md`, *The sample's mix of strata*](metrics/approximately.md#the-samples-mix-of-strata);
- with many strata, about 1 in 20 margins misses the true value by chance, so one stratum that looks unusually good or bad is not, alone, a finding. The report says so beside the table.

### Twins

A [twin](../docs/terminology.md#7-evaluating-extraction-step-070) is an evaluated record with the same title, the same `notes`, or both as a record the [current schema](../docs/terminology.md#6-extracting-with-a-schema-step-060) was learned from. Step 030 keeps the pool and the [induction candidates](../docs/terminology.md#4-ground-truth-and-samples) apart, so that 070 measures extraction on text the schema was not learned from. But two different records can carry the same `notes`: a series of datasets often repeats the same `notes` under different titles, and sometimes one title over different `notes`. The schema has then seen some or most of a twin's text, and its numbers may flatter extraction.

**In the report.** In each part's subsection *Metrics: … part* of the report (`outputs/reports/070_evaluate_<date>_<time>.md`, section *Results*), the table *Twins* names the twins by [pool position](../docs/terminology.md#4-ground-truth-and-samples) and id, each with its [twin kind](../docs/terminology.md#7-evaluating-extraction-step-070), and gives precision, recall, and F1 for all evaluated records beside the same numbers without the twins of every kind. If the two columns differ by more than their margins, report the column without the twins. `metrics.json` has the same, under each part's `twins`. The headline (top of the report, and the pipeline report's table *Pipeline at a glance*) gives the number of twins among the evaluated [tuning records](../docs/terminology.md#7-evaluating-extraction-step-070). Steps 030 and 040 count the twins in the whole pool, in the same table (code: `common/common_helpers/ground_truth.py`, `twin_table`): 030 against every induction candidate (the most there can be), 040 against the texts it learned from as well (section *Results*, subsection *Twins in the pool*, of each step's report).

**Which records the current schema was learned from.** Step 060 writes them in `schema_used.json`, key `learned_from`:

- the [induced schema](../docs/terminology.md#5-learning-the-schema-step-040): the texts that same run of 040 learned from (`040_induce_schema/induction_evidence.json`, key `texts`), 150 with the default settings;
- the [ground truth schema](../docs/terminology.md#3-schemas): pool positions 0–5, which it was written while annotating;
- either way, also any pool record a [schema entry](../docs/terminology.md#3-schemas)'s source line names (`source: ground truth tuning #12`).

For any other [schema file](../docs/terminology.md#6-extracting-with-a-schema-step-060) (e.g. an older schema kept elsewhere), they aren't known, unless 040's `induction_evidence.json` of the same run is beside it. The report then warns, marks no record, and gives no numbers without twins.

**Twin kinds.** Each compares the pool record with one record the schema was learned from. Titles and `notes` are compared [evened out](../docs/terminology.md#2-triples); an empty one is never the same as another.

- *whole text*: the same title and the same `notes`;
- *notes only*: the same `notes`, a different title;
- *title only*: the same title, different `notes`.

A record with two kinds, with two different records, gets the one that shares more text: whole text, then notes only, then title only. *Suppose:* pool record A has the same `notes` as learned-from record X, and the same title as learned-from record Y. *Then:* A is *notes only*, since the `notes` hold more of the facts. Code: `common/common_helpers/ground_truth.py`, `twin_kinds`.

**Why these kinds, and why only the records the schema was learned from.** Two choices had to be made: which fields to compare, and against which records. Counted on 2026-10-12 (the 2026-10-01 harvest, 999 pool records), each number a count of pool records:

- Compared with all 35,407 induction candidates: 388 are whole-text twins of one of them, 129 notes-only, and 24 title-only (541 twins).
- Compared with the 150 texts 040 learns from (default settings): 3 are whole-text twins of one of them, 18 notes-only, and none title-only (21 twins).
- Compared with the records the ground truth schema was written from (pool positions 0–5): only those 6 records themselves.

Only the records the schema was learned from matter: a pool record that repeats an induction candidate 040 never read can't flatter the schema. The twin kinds say how much of a twin's text the schema saw. Most facts are stated in the `notes`: of the 150 [classed triples](../docs/terminology.md#2-triples) of the [ground truth](../docs/terminology.md#4-ground-truth-and-samples) and of the old [drafted batches](../docs/terminology.md#4-ground-truth-and-samples) (`annotations/archive/`) that have a [source text](../docs/terminology.md#1-records-and-their-text), 140 had it in the `notes` and 10 in the title. So a notes-only twin shares most of its facts' wording, and a title-only twin a few (e.g. a version, "V1.0"). Comparing whole texts alone would miss both (3 twins instead of 21, on 040's texts).

**Limits.** A `title` or `notes` that is nearly the same (one number or one word different, as in a series of datasets) doesn't make a twin. Such near-twins may flatter extraction too; nothing measures them yet.

## Prompts

| Prompt file | Sent in | Asks the model to |
|---|---|---|
| `070_evaluate/070_evaluate_prompts/map_component_classes.txt` | [stage](../docs/terminology.md#8-the-pipeline) 2, one call per 100 [component classes](../docs/terminology.md#3-schemas) (`TRANSLATE_BATCH` in `component_classes.py`, so no answer grows past the length limit), only for component classes of the [current schema](../docs/terminology.md#6-extracting-with-a-schema-step-060) without a row | for each of those component classes, give the component class of the [ground truth schema](../docs/terminology.md#3-schemas) that means the same thing (or none), and say whether a [predicate](../docs/terminology.md#3-schemas) states the relation in the opposite direction; the ground truth schema's component classes and definitions are shown in the prompt |

## Audit trail

- **Prompts.** The [report](../docs/terminology.md#8-the-pipeline)'s *Prompts* section lists every prompt the [run](../docs/terminology.md#8-the-pipeline) filled in, each with a [fingerprint](../docs/terminology.md#8-the-pipeline) (sha256) of its exact text, so the prompt behind any answer is known even if the prompt file was edited later (`_manifest.json` keeps the full fingerprints).
- **[Log](../docs/terminology.md#8-the-pipeline).** `outputs/logs/<run id>.log` records the command line, the [settings](../docs/terminology.md#8-the-pipeline), the git commit, the [model call](../docs/terminology.md#8-the-pipeline)'s retries (if any), each [move](../docs/terminology.md#8-the-pipeline)'s duration, each output file's hash and, on failure, the full traceback.
- **[Origin](../docs/terminology.md#8-the-pipeline).** Each row of `compared_triples.csv` has an `origin` column naming the [extracted triple](../docs/terminology.md#6-extracting-with-a-schema-step-060) it compares (`060_extract/extracted_triples.csv#<position>`) and the [ground truth](../docs/terminology.md#4-ground-truth-and-samples) triple (`annotations/ground_truth/batch_000.csv#<position>`); the ground truth is made by a person, so a trace stops there.
- **Trace.** `py helpers/audit.py <record id>` follows a [record](../docs/terminology.md#1-records-and-their-text) back through every [step](../docs/terminology.md#8-the-pipeline)'s output to the 010 [batch file](../docs/terminology.md#1-records-and-their-text) and the API request that first returned it (`helpers/audit.md`).
- **[Held-out looks](../docs/terminology.md#7-evaluating-extraction-step-070).** `annotations/held_out_looks.csv` keeps one line per look at the [held-out part](../docs/terminology.md#7-evaluating-extraction-step-070), in Git.

## Known limits

- **Not yet run with the real [model](../docs/terminology.md#8-the-pipeline).** As of 2026-09-29, 070 has been tested only with a hand-made 060 output whose right answers were worked out in advance (all 16 numbers came out as expected), and with synthetic [records](../docs/terminology.md#1-records-and-their-text) for the margins; 060 itself hasn't [run](../docs/terminology.md#8-the-pipeline) with the real model yet, because the model's services can't be reached from the laptop it was built on. The numbers in this guide come from those tests, not from a real run. Since 2026-10-12, the model's service is reached from the NASA laptop, where step 040 made, with the real model, the schema that 060 and 070 start from ([`findings.md`](../docs/findings.md#2026-10-12--step-040--the-baseline-schema)); no 070 run on a real 060 output is recorded there yet.
- **One translation per [component class](../docs/terminology.md#3-schemas).** A component class of the [current schema](../docs/terminology.md#6-extracting-with-a-schema-step-060) translates to at most one component class of the [ground truth schema](../docs/terminology.md#3-schemas); if it covers two (e.g. `Instrument` (current schema) for both `Instrument` and `Sensor` (ground truth schema)), pick the closer one.
- **Partial pairing can be fooled**, and doesn't catch the same [fact](../docs/terminology.md#2-triples) in different words ("the satellite" for "Aqua"), which understates precision and recall: see `metrics/pairs.md`, *Assumes and can't see*. You review the [tuning part](../docs/terminology.md#7-evaluating-extraction-step-070)'s [partial pairs](metrics/pairs.md); the [held-out part](../docs/terminology.md#7-evaluating-extraction-step-070)'s aren't reviewed until the pipeline is frozen for the final evaluation (looking at them earlier would mean looking at it). Before you review them there (at the final evaluation), the held-out part's partial level may count pairs that aren't the same fact. Its exact level can't be fooled this way, so read the held-out part's exact numbers as its main ones.
- **The [ground truth](../docs/terminology.md#4-ground-truth-and-samples) started as [drafted triples](../docs/terminology.md#4-ground-truth-and-samples)**: [recall](../docs/terminology.md#7-evaluating-extraction-step-070) is likely overstated (see [`metrics/recall.md`](metrics/recall.md), *Assumes and can't see*).
- **The threshold of 20 records** for a margin is a rule of thumb.
