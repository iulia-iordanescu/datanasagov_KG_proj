# 040_induce_schema

Terms ([triple instance](../docs/terminology.md#2-triples), [component instance](../docs/terminology.md#2-triples), [label](../docs/terminology.md#5-learning-the-schema-step-040), [support](../docs/terminology.md#5-learning-the-schema-step-040), …) are as defined in [docs/terminology.md](../docs/terminology.md), especially section *Learning the schema (step 040)*.

## Purpose

Learns the [schema](../docs/terminology.md#3-schemas) from the catalog itself, instead of writing it in advance:

- **[entity classes](../docs/terminology.md#3-schemas)**: the types of things the [texts](../docs/terminology.md#1-records-and-their-text) talk about, e.g. `Instrument`, `Spacecraft`;
- **[predicates](../docs/terminology.md#3-schemas)**: the relationships between them, e.g. `ABOARD`;
- **[patterns](../docs/terminology.md#3-schemas)**: which entity classes each predicate joins, e.g. `Instrument ABOARD Spacecraft`.

A [model](../docs/terminology.md#8-the-pipeline) reads a sample of texts, the same number from each stratum of the [ground truth candidates pool](../docs/terminology.md#4-ground-truth-and-samples), and lists the [triple instances](../docs/terminology.md#2-triples) they state, with no schema imposed; code keeps only those it can verify in the text. The model gives every [component instance](../docs/terminology.md#2-triples) a [label](../docs/terminology.md#5-learning-the-schema-step-040), merges labels that mean the same thing, splits a predicate that stands for different relationships by the entity classes of its subjects, its objects or both, and merges the predicates again. Code counts the [support](../docs/terminology.md#5-learning-the-schema-step-040) of each [schema entry](../docs/terminology.md#3-schemas) (how many texts, and how many [maintainers](../docs/terminology.md#1-records-and-their-text), back it), and keeps every schema entry with that [evidence](../docs/terminology.md#5-learning-the-schema-step-040). The schema is judged downstream: 070 measures how much of the [ground truth](../docs/terminology.md#4-ground-truth-and-samples) it can express (its [recall upper bound](../docs/terminology.md#7-evaluating-extraction-step-070)) and how well extraction does with it.

## How to run

From the repository folder, with the environment active (`docs/virtual_environment_setup.md`), on a computer that can reach the model's service and has its key in `.env` (`docs/running_on_nasa_laptop.md`):

```
py 040_induce_schema/run.py --help                           every input and setting, with its default
py 040_induce_schema/run.py                                  learn from 152 texts (8 per stratum); asks before paying
py 040_induce_schema/run.py --texts_per_stratum 16           learn from more text
py 040_induce_schema/run.py --confirm_paid_calls false       don't ask (unattended runs)
```

**Paying.** Before its first [model call](../docs/terminology.md#8-the-pipeline), 040 logs its plan (how many extraction calls, the [model](../docs/terminology.md#8-the-pipeline)) and waits: Enter starts (the answers that go ahead, and the ones that stop it having spent nothing: `docs/running_on_nasa_laptop.md`, section 5). If the [run](../docs/terminology.md#8-the-pipeline) can't do exactly what you asked, it says so first, above the question (*Step 040 found N warnings:*, then each one, numbered; they're listed under *Checks and warnings*). Its first call is the [test call](../docs/terminology.md#8-the-pipeline), which checks that the model name and key work. A run whose answers are all in the cache never asks and never pays. Model calls: about one per [text](../docs/terminology.md#1-records-and-their-text) to extract [triple instances](../docs/terminology.md#2-triples), plus a few dozen to [label](../docs/terminology.md#5-learning-the-schema-step-040), merge, split, and define; the [report](../docs/terminology.md#8-the-pipeline) counts each [stage](../docs/terminology.md#8-the-pipeline)'s calls exactly.

**The cache.** Every model answer is kept in `cache/`, under a [fingerprint](../docs/terminology.md#8-the-pipeline) of everything that decided it (every part, and what isn't one: `docs/running_on_nasa_laptop.md`, section 5, *What a saved answer depends on*). A rerun reuses every answer whose fingerprint is unchanged: a failed call isn't kept, so a rerun asks only the calls that failed (but an answer cut off at the length limit is kept as cut off, and not asked again with the same settings: *A cut-off isn't paid for twice* in `docs/running_on_nasa_laptop.md`, section 5). Only an answer of the shape the step reads is kept (a `"triples"` list for extraction, a `"labels"` object for labeling, a `"merges"` list for merging, a `"splits"` list for splitting, a `"definitions"` object for defining): one of another shape is asked once more, saying what was wrong, then counts as a failed call; one kept by an earlier version of the code is asked again, and the report's warnings name the cache file (`shape_error` in `common/common_helpers/extraction.py`; `ask_cached` and `Cache.get` in `common/common_helpers/cache.py`). Editing a prompt asks again exactly the calls that use it (a file of `common/common_prompts/`: 040's, 050's, and 060's); deleting `cache/` (or all of `outputs/`) means paying for every call again. Taking more texts (a higher `texts_per_stratum`) reuses every text's extraction already made and pays only for the new texts.

## How it works

Eight [stages](../docs/terminology.md#8-the-pipeline), in `040_induce_schema/run.py`'s `main()`; stages 2, 3, 4, 5, and 7 ask the [model](../docs/terminology.md#8-the-pipeline), the others are code:

1. **Pick the [texts](../docs/terminology.md#1-records-and-their-text)** (*selection*; `texts.py`, `pick_texts`). A stratified draw over the same 19 strata as the [ground truth candidates pool](../docs/terminology.md#4-ground-truth-and-samples) (`pool_design`: 18 [maintainers](../docs/terminology.md#1-records-and-their-text) with a stratum of their own, and "(small maintainers)" for the 404 others), with equal allocation: `texts_per_stratum` texts from each stratum, 152 by default. The purpose is discovery (finding the [entity classes](../docs/terminology.md#3-schemas) and predicates the catalog's texts use), not estimation: a small stratum's texts can show a predicate only its maintainers use, while allocation in proportion to size would give the small strata almost no texts. So every stratum gets the same number, as the design of the Technical Memorandum had it. Only [induction candidates](../docs/terminology.md#4-ground-truth-and-samples) are drawn ([records](../docs/terminology.md#1-records-and-their-text) outside the pool, with text), each stratum's in a fixed random order: for a maintainer's own stratum, 030's order of its candidates; for "(small maintainers)", the stratum's candidates shuffled the way 030 shuffles a maintainer's (the same seed, `induction_seed` in `splits.json`, with the stratum's name in place of the maintainer's). The strata are drawn in rounds, one text from each stratum per round, so taking more texts later keeps every text taken before. While drawing, a text that is a twin of a text already drawn is skipped and the next in its stratum's order taken: a *whole text* twin (the same title and `notes`) or a *notes only* twin (the same `notes`, another title), as `common/common_helpers/ground_truth.py`'s `twin_kinds` defines them (compared [evened out](../docs/terminology.md#2-triples)). A *title only* twin (the same title, other `notes`) is kept, since its text differs. The report counts both, per stratum (*What this run worked on*). Only these exact twins are skipped: see *Known limits*. A maintainer the pool's design doesn't name (one that joined the catalog after the pool was drawn) is counted with "(small maintainers)", with a note. The texts are then read in a random order fixed by the same seed, so no stratum comes first: reading the first k texts is then a random draw of k, which is what the saturation curve averages over (*Saturation*). Each text is the record's title and notes (and any extra text [fields](../docs/terminology.md#1-records-and-their-text) 020 kept), split into [text pieces](../docs/terminology.md#1-records-and-their-text) only if it's longer than `max_chars`, with the title repeated at the top of each piece (when the title is shorter than a quarter of `max_chars`).
2. **Extract [triple instances](../docs/terminology.md#2-triples), and check them** (`extract.py`, `extract_triple_instances`). One [model call](../docs/terminology.md#8-the-pipeline) per text piece: list every [fact](../docs/terminology.md#2-triples) the text states as a triple instance, with the text's own words as its [subject instance](../docs/terminology.md#2-triples) and [object instance](../docs/terminology.md#2-triples) and a short verb phrase in the model's words as its [predicate instance](../docs/terminology.md#2-triples) ("MODIS" – "is aboard" – "Aqua"), each with its [source text](../docs/terminology.md#1-records-and-their-text), the shortest passage that states it, copied exactly. Nothing tells the model which entity classes or predicates to look for. Everything else is step 060's (`common/common_helpers/extraction.py`), so the [schema](../docs/terminology.md#3-schemas) is learned from the same type of facts extraction later has to produce: the extraction rules; the prompt's layout and order (the rules, the task, the shared two passes of `common/common_prompts/extraction_passes.txt`, the reply format, the record, and the shared closing line); the reply format (without entity classes, which stage 3 learns); prompt caching of everything before the record, for Anthropic's models (`060_extract/060_extract.md`, *Prompt caching, for cost*); the duplicate count (below); and the model calls themselves (a text with a failed call is left out whole, and asked again on the next run). Its task requires two differences, listed in `tests/allowed_differences.txt` with their reasons: no schema is given, and no worked examples, since those come with an example schema and answers written with its entity classes and predicates, which would steer the schema 040 learns from the records. Until 2026-11-14 the prompt had a layout of its own (the task first, its own completeness paragraph, no two passes, no prompt caching). The reply also names the [describes class](../docs/terminology.md#2-triples) (`describes_class`): the entity class of [the title's instance](../docs/terminology.md#2-triples) ("Dataset", "WebTool", …), judged from the whole text; the one the most text pieces named decides it (compared as a [loose match](../docs/terminology.md#3-schemas); on a tie, the first named, in its first spelling), as in 050 and 060 (`common/common_helpers/extraction.py`, `describes_class`). Until 2026-11-15 the first piece to name one decided it. [Steps](../docs/terminology.md#8-the-pipeline) 050 and 060 need such entity classes for every record's [describes triple](../docs/terminology.md#2-triples), so this makes sure the schema has them. Then code checks every triple instance against its record's whole text (`common/common_helpers/validate.py`, shared with 050 and 060):
   - **[unverified](../docs/terminology.md#2-triples), left out** (may be invented): a triple instance with no source text, or whose source text isn't in the text. It counts toward nothing in the later stages, and is listed in `induction_evidence.json` with why, under `errors`: `no_source_text` or `source_not_in_text` (both errors, as 050's guide lists them, *Checks on each row*);
   - **verified, flagged**: a triple instance whose [subject](../docs/terminology.md#2-triples) instance or [object](../docs/terminology.md#2-triples) instance isn't in the text or in its own source text (usually reworded, "the instrument" for "MODIS"), or whose subject instance and object instance are the same, or that disagrees with rule 20's abbreviation test (the test of Schwartz and Hearst, 2003: `common/common_helpers/abbreviations.py`): the [flags](../docs/terminology.md#2-triples) `subject_not_in_text`, `object_not_in_text`, `subject_not_in_source`, `object_not_in_source`, `subject_equals_object`, `abbreviation_fails_test`, `also_known_as_fails_test`, `identifier_passes_test`, `abbreviation_spelled_out` (as 050's guide explains them, *Checks on each row*). The flags are counted in the [report](../docs/terminology.md#8-the-pipeline), of [verified triple instances](../docs/terminology.md#2-triples) only.

   How the two relate: the errors decide first. A triple instance with any error is unverified; every other one is verified: the two exclude each other, and every triple instance is one of them. Flagged is a subcase of verified: a verified triple instance with at least one flag. An unverified triple instance may raise flags too, but they aren't counted. "In the text" means found once evened out. A triple instance two pieces of one text both state counts once (the same fact as 050 and 060 judge it: `common/common_helpers/triples_io.py`, `triple_key`, which compares the instances and the predicate instance with case and punctuation evened out), the first copy that passes the checks kept (so a first copy with a wrong source text doesn't make it unverified); an item that isn't a triple instance is dropped and counted.
3. **[Label](../docs/terminology.md#5-learning-the-schema-step-040) every [component instance](../docs/terminology.md#2-triples), with a [running vocabulary](../docs/terminology.md#5-learning-the-schema-step-040)** (*labeling*; `label.py`, `label_component_instances`). A subject or object instance gets an entity class label ("MODIS" → `Instrument`); a [predicate](../docs/terminology.md#3-schemas) instance gets a predicate label ("is aboard" → `ABOARD`). Each is judged by the shortest triple instance it appears in, sent with that triple instance's source text (the passage of the record that states it, which stage 2 keeps): a triple instance alone may not say what a thing is. *Suppose* the shortest triple instance with "Dawn" is "Dawn" – "carries" – "GRaND". *Then* Dawn could be a mission or a spacecraft, while its source text, "the GRaND instrument aboard the Dawn spacecraft", says which. Predicate instances are sent the same way, so both kinds are judged alike. The idea is TRACE-KG's (Abolhasani, Ba, He & Pan, "Traceable Context-Enriched Knowledge Graph Generation with Induced Schemas", arXiv:2604.03496v3, [paper](https://arxiv.org/abs/2604.03496v3)): its prompt for entity classes gives the model context for each thing as its "PRIMARY evidence for meaning" (`TKG_Prompts.py`, line 419); there the context is the model's own words, here the record's. A text's title isn't sent: its label is its `describes_class` from stage 2, and those labels start the running vocabulary of entity class labels (most common first), so subject and object instances reuse them. The running vocabulary shows one spelling of each label: a label that differs from one already in it only in case, spacing or punctuation (a loose match) isn't added to it again, so no batch is shown two spellings of one label; the component instances keep the label as the model gave it, and stage 4 folds the spellings. The component instances go to the model in batches of 80, most common first, and every batch is shown the labels chosen so far, with the instruction to reuse one whenever it fits and coin a new one only when none does. So one idea doesn't end up under several labels because its component instances were in different batches. One left unlabeled is asked once more; if still unlabeled, it's listed and counts toward no [schema entry](../docs/terminology.md#3-schemas).
4. **Merge synonymous labels** (*merging*; `merge.py`, `merge_labels`), the first of step 040's two kinds of [canonicalization](../docs/terminology.md#5-learning-the-schema-step-040). First, code makes labels that differ only in case, spacing, or punctuation one, the most frequent spelling (the one most component instances got; on a tie, the first in alphabetical order): a [spelling fold](../docs/terminology.md#3-schemas), the second kind of canonicalization (digits are kept: `Level2` and `Level3` stay apart); every fold is listed in `induction_evidence.json` (the report shows the first 20). Folding comes before the merge call, so the model is never shown two spellings of one label (until 2026-11-15 it came after the merge). A few synonyms can still slip through stage 3, so the finished list of labels goes to the model in one call per kind (entity class labels, predicate labels), each label with the number of texts it was found in and examples: an entity class label with the subject or object instances that most often got it (a text's title counts under its `describes_class`, as in stage 6, so a label used only for titles has its texts and titles too); a predicate label with up to 3 triple instances that state it, the most frequent first (ties in reading order), each written "subject instance (entity class) -- predicate instance -- object instance (entity class)", with the entity classes as this stage's entity class merge, which runs first, left them (until 2026-11-15, its predicate instances only). The predicate prompt states the verb test, as splitting's does: two labels name one predicate when one verb describes what the subject and object have to do with each other in both, whatever their entity classes; different entity classes alone are no reason to keep two labels apart, and the same predicate instance alone is no reason to merge them. Every label is seen beside every other. The model lists only the merges it finds (`Sensor` → `Instrument`); predicates pointing in opposite directions are never merged. Code checks the reply: a merge must go into a label that was sent; labels that weren't sent are ignored; a label merged twice keeps the first merge; chains are followed to their end. Every merge is listed in the report (`outputs/reports/040_induce_schema_<date>_<time>.md`), section *Results*, subsection *Triple instances and labels*. Each component instance's final label (stage 3's label, folded by spelling, then merged) is what stages 5 and 6 read.
5. **Split a predicate by its subject's or object's entity class, or both, then merge again** (*splitting*; `split.py`, `split_predicates`). A predicate can still cover relationships that differ by what its subject is, by what its object is, or by the two together. *Suppose* SOURCED_FROM ([current schema](../docs/terminology.md#6-extracting-with-a-schema-step-060)) has triple instances with Mission objects ("data from the Apollo 11 mission": which mission produced the data) and with Spacecraft objects ("images from the Cassini spacecraft": which spacecraft carried the instrument). *Then* one predicate for each says more, and each can translate to its own predicate of the [ground truth schema](../docs/terminology.md#3-schemas) (FROM_MISSION, FROM_PLATFORM). Only a triple instance whose subject, predicate and object all have a final label (stage 4) has a pattern, so only such triple instances are grouped, shown to the model, counted toward a split and moved; one with an unlabeled subject or object stays with its predicate. Every predicate whose triple instances have more than one subject entity class or more than one object entity class (so more than one pattern) goes to the model, 20 at a time, with each of its patterns, the number of texts it was found in and up to 3 of its triple instances, the number of texts of each of its subject entity classes and object entity classes, and the names of every predicate found (the final labels of stage 4), which a new predicate may not take. The model proposes [predicate splits](../docs/terminology.md#5-learning-the-schema-step-040) only where the predicate stands for different relationships, by this test, which the prompt states once: group its triple instances by the entity class of their subject, of their object, or of both (their pattern); if describing what the subject and object have to do with each other takes a different verb for each group, the predicate stands for different relationships, and is split, one new predicate per relationship; if one verb fits every group, it stays whole, since the entity classes already record the difference (the prompt's invented examples: PRODUCED_BY splits by object when its Instrument objects measured the data and its Organization objects processed them; COVERS_AREA stays whole when its objects are a Country or a Region, since the data cover both; until 2026-11-15 a predicate was grouped by its object's entity class only). A predicate split is a new predicate with its grouping (subject, object or pattern) and the groups it takes (entity classes, or patterns written "Subject -> Object"); a group no predicate split takes stays with the predicate. All the predicate splits of one predicate use one grouping, that of its first predicate split that passes the checks. Two groupings would let one triple instance belong to two new predicates (a subject split taking Dataset and an object split taking Mission both claim the pattern Dataset -> Mission), and any mix of subject groups and object groups is a set of patterns, which the pattern grouping can say. Code checks each predicate split, in this order, and rejects it at the first check it fails: it is a JSON object; its predicate is one that was sent; it names a new predicate; that name is neither the name of a predicate found (the one split included) nor one an earlier predicate split took (compared as a loose match); its grouping is subject, object or pattern; it is the grouping of the predicate's earlier predicate splits; it names at least one group; each group is the predicate's own (an entity class the predicate has only on the other side is not); no earlier predicate split of that predicate took any of them (the first split stands, as the first merge does); it doesn't take every group of the predicate (that would rename the predicate, not split it); and its supporting texts (the texts with a triple instance it would take) number at least `min_split_texts` (*Settings*). Every rejected predicate split is listed, with why, in the report's section *Splitting*. Then `max_new_predicates` caps how many predicates the kept predicate splits add: a predicate split into n new predicates adds n, or n − 1 when its predicate splits take every group it has (the predicate itself is then left with no triple instance that has a pattern). If the predicate splits that passed the checks would add more, they are kept one at a time, the one with the most supporting texts first, each only if the total stays within the cap; the others are dropped and listed, and their predicates keep those triple instances. After the cap, the predicates are merged again (*merging again*): every predicate after splitting, old and new, goes to the model in one call with stage 4's predicate merge prompt, shown as stage 4 shows a predicate (a new predicate's examples are triple instances its split took, so the parts of one split arrive with their different entity classes, not only their shared words), read and checked by stage 4's code, and its answer is cached apart from stage 4's; spelling folds apply first, as in stage 4. The cap comes first because it bounds the predicates the kept predicate splits add and a merge can only lower that number, so a merge never makes room for a predicate split the cap left out. A merge of two predicates that were both there at stage 4 is set aside, since stage 4's call already judged that pair. When every part of a split predicate (its new predicates, and the predicate itself if it kept triple instances) ends in one predicate, the split is undone: its new predicates are dropped, and the predicate, whole again, goes to that predicate, or stays itself when that predicate is one of its own parts; undoing one split can undo another in turn. Code pins each new predicate to the groups its split took ("any" for the side not grouped by): "Dataset -> any", "any -> Mission", or the patterns themselves. A predicate that merging again made of several is pinned to the union of their pins when each of them is pinned, and has no pin when any of them has none, since a predicate with no pin may join whatever entity classes its meaning fits. Every undone predicate split, merge, fold and pin dropped is recorded. Stage 6 then gives each triple instance of a split predicate whose pattern is in a group a kept predicate split took that predicate split's new predicate, then the predicate merging again made of it. Splitting reads only the [induced schema](../docs/terminology.md#5-learning-the-schema-step-040)'s own labels and triple instances, never the [ground truth](../docs/terminology.md#4-ground-truth-and-samples) or the [translation table](../docs/terminology.md#7-evaluating-extraction-step-070). From TRACE-KG (Abolhasani et al., above): its model may split an entity class into several (`split_class`, appendix B.4.2), and its code keeps only the split entity class's own members, each in one split only (`execute_split_class`, `TKG_Main.py`, line 4796); it sets each triple instance's predicate with its subject's and object's entity classes in view (section 4.5); and its code carries out only actions it has checked (section 4.6). Here the split is of a predicate, by its subject's or object's entity class or both.
6. **Count the [evidence](../docs/terminology.md#5-learning-the-schema-step-040)** (*counting*; `count.py`, `count_support`). Each verified triple instance becomes, through the final labels of its component instances and the splits of stage 5, a [subject class](../docs/terminology.md#2-triples), an [object class](../docs/terminology.md#2-triples), a predicate, and, if all three are labeled, a [pattern](../docs/terminology.md#3-schemas). Each text's title also counts once toward its label, as an entity class, whether or not it is in a triple instance. For every schema entry: its [support](../docs/terminology.md#5-learning-the-schema-step-040), which texts, and which maintainers.
7. **Write definitions** (*defining*; `define.py`, `write_definitions`). Every entity class and predicate whose support reaches `min_support` goes to the model, 40 at a time, with its support and up to 5 examples (stage 6's; `the_schema.json` keeps the first 3), for one defining sentence each, or a reason if it's too vague to tell anything apart ("Thing"). A predicate is also sent with its patterns from stage 6 (the entity classes of its subject and object, each pair with its support) through entity classes being defined, and both prompts list the entity classes being defined: a definition may name any of them, spelled as listed, when that makes it clearer ("was collected during this Mission"), as the ground truth schema's definitions do; it never has to. No prompt shows a schema's patterns or pins (`common/common_helpers/schema_io.py`, `schema_text`), so a predicate's definition is the one place a model learns what it joins. A predicate stage 5 pinned is also sent with `must_name`, the entity classes of its pin being defined, and its definition must name each of them (the check the ground truth schema's pins pass: `common/common_helpers/schema_io.py`, `unnamed_pinned`); the prompt shows those entity classes, never the pin itself. Code then checks the replies, and asks once more, as stage 3 does for a component instance left unlabeled, about an entry that was neither defined nor called too vague, about a [pinned predicate](../docs/terminology.md#3-schemas)'s definition that doesn't name every entity class of its `must_name`, and about a definition that names a word shaped like an entity class (two or more capitalised parts each followed by lowercase letters, such as `PhysicalQuantity`; a plural "s" or "es" allowed) that is no entity class being defined, e.g. one a merge removed or one below `min_support`. Words such as `MODIS`, `SeaWiFS`, `GeoTIFF` or `NetCDF` (a part without lowercase letters after its capital) and one-part words (`Instrument`) are never taken for one, so proper nouns of the domain aren't flagged, though a CamelCase one (`McMurdo`) is. The second reply's definition replaces the first; when the second gives none, the first is kept; either way a definition that still names such a word, or still doesn't name its pin, is kept, recorded in `discarded.jsonl` (as replaced) and listed in the report's warnings. This stage only writes words; it merges and chooses nothing.
8. **Build the schema** (*the schema stage*; `check.py`, `check_schema`). The schema is built from stage 6's counts, never from the model's replies: an entity class or predicate is in it if its support reaches `min_support` and it isn't too vague; a pattern is in it if its support reaches `min_support` and its two entity classes and its predicate are in it. A pinned predicate keeps its pin (`pinned`), less any pair naming an entity class not in the schema; one left with no pair is [deferred](../docs/terminology.md#5-learning-the-schema-step-040), as a pattern through such an entity class is. Every other schema entry is deferred, with its reason. A schema entry missing its definition stays in, marked, and is listed.

Stages 2 and 3 follow AutoSchemaKG (Bai, Fan, Hu et al., "AutoSchemaKG: Autonomous Knowledge Graph Construction through Dynamic Schema Induction from Web-Scale Corpora", 2025, arXiv:2505.23628v3, [paper](https://arxiv.org/abs/2505.23628v3), sections 3.1 and 3.2): [triples](../docs/terminology.md#2-triples) extracted with no schema imposed ([open extraction](../docs/terminology.md#6-extracting-with-a-schema-step-060)), then a general type for each subject instance, object instance, and predicate instance, asked of the model in batches (its "conceptualization" [labeling]). AutoSchemaKG gives each one at least three types, at different levels of abstraction, where stage 3 gives one label; it has no stage like 4, 5, 6, or 7 (merging labels, splitting predicates, counting support, writing definitions).

Then, for the report only, **the induced schema is put beside the ground truth schema** (`compare.py`, code, comparing [component classes](../docs/terminology.md#3-schemas) with `common/common_helpers/triples_io.component_class_key`): which entity classes, predicates, and patterns both have, which only the ground truth schema has, and which only the induced one has. Component classes match when they are a loose match, so a concept the two name differently (`Instrument`, `Sensor`) counts as unmatched. It's a sanity check on what the data taught the model, not a metric: 070 measures how much of the ground truth the schema can express.

**Then the results** (`results`): `the_schema.json` and `induction_evidence.json` are written, replacing the last run's (whose versions are kept in `previous_runs/<run id>/` when they differ: `helpers/audit.md`, *Where to look*); the report. Its subsection *Twins in the pool* (section *Results*) counts the pool records with the same title, the same `notes`, or both as one of the texts this run learned from, by [twin kind](../docs/terminology.md#7-evaluating-extraction-step-070), beside the same counts against every induction candidate (`070_evaluate/070_evaluate.md`, *Twins*). The headline (top of the report, and the pipeline report's table *Pipeline at a glance*) gives the number of twins in the pool. The report's subsection *Triple instances and labels* (section *Results*) starts with a table, *Triple instances per text*, computed in code from each text's `triple_instances` and `unverified` in `induction_evidence.json` (one text is one record's text): for each text, how many triple instances the model listed (row *raw*: verified + unverified) and how many are verified (row *verified (kept)*), given as the number of texts, min, max, mean, median, standard deviation (SD), total, and texts with none. A triple instance two text pieces of a text both state counts once; items that weren't triple instances, and texts whose model call failed, aren't counted. The headline, and `_manifest.json`, also give both totals and their means per text (`raw triple instances`, `verified triple instances`), the twins skipped while drawing, the predicates added by splitting, the texts with no verified triple instance, and the model calls that failed.

**Statistics** (code: `tally.py`; the same numbers are in `induction_evidence.json`, key `statistics`). In the report's section *Results*: subsection *What this run worked on* gives, per stratum, its maintainers, its induction candidates, the texts drawn, the texts skipped as whole-text twins and as notes-only twins, and the title-only twins drawn and kept, with every skipped text's record id. Subsection *Triple instances and labels* gives, after the table above, the same numbers for verified triple instances per text by stratum, and the texts whose replies listed no triple instance, or none verified, each with its record id and stratum. Subsection *Splitting* lists the predicate splits kept, dropped and rejected, and the schema text's length (*Settings*, `max_new_predicates`). Subsection *Code checks* gives what each code check of stages 2 to 8 removed: for the checks on triple instances (stage 2: not a triple instance, stated twice, unverified; stage 6: a component instance without a final label, so no pattern; stage 8: a pattern not in the schema), how many triple instances each removed and the texts it removed wholly, each with its record id and stratum (a check removes a text wholly when the text had at least one triple instance just before the check and none after it); for the checks on the model's other answers (labels, merges, predicate splits, definitions) and on the schema entries (deferred, by reason), how many each removed. Subsection *Model calls* ends with the calls that failed, and those cut off, by stage.

The code: `040_induce_schema/` holds `run.py` (the [control panel](../docs/terminology.md#8-the-pipeline): inputs, [settings](../docs/terminology.md#8-the-pipeline), and the [moves](../docs/terminology.md#8-the-pipeline), in order); `040_induce_schema/040_induce_schema_helpers/` holds `moves.py` (the moves, and writing the results), one file per stage (above), `compare.py`, `saturation.py`, and `tally.py`; `040_induce_schema/040_induce_schema_prompts/` holds the prompts (see *Prompts*). Shared with other steps: `common/common_helpers/validate.py` and `common/common_helpers/text_match.py` (the checks), `common/common_helpers/schema_io.py` (reading the ground truth schema), `common/common_helpers/chunking.py` (text pieces), `common/common_helpers/cache.py` (the answer cache), `common/common_helpers/llm.py` (the model).

**Why "undefined" is a stratum:** it is the 5th largest maintainer (989 records whose maintainer the catalog itself gives as `undefined`), so the pool gave it a stratum of its own; see `030_split/030_split.md`, *Why "undefined" counts as a maintainer*.

### Saturation

Would more texts have added schema entries? After counting (stage 5), and with no [model call](../docs/terminology.md#8-the-pipeline), the report's subsection *Saturation* (section *Results*) answers with a curve and a table (code: `040_induce_schema/040_induce_schema_helpers/saturation.py`; the numbers are also in `induction_evidence.json`, key `saturation`).

**The curve.** For k = 25, 50, … texts, how many [entity classes](../docs/terminology.md#3-schemas), predicates, and patterns would have reached `min_support` had 040 read only k of its texts. *Suppose* 040 read 4 texts with `min_support` 2, and an entity class was found in T1, T2, and T3. *Then* read in the order T1, T2, T3, T4 it enters the schema after 2 texts; read T4, T1, T3, T2, after 3. No order is the right one, so the curve averages over every order the texts could have been read in (stage 1 reads the texts in one random order, so the curve's average is over orders of the same kind). It does so exactly, by a formula (the hypergeometric probability that k texts drawn from the N include at least `min_support` of the entry's texts, summed over the schema entries), with no random draw. The column *Added by the last 25 texts* is the one to read: near 0, more texts of the same type would barely change the schema; well above 0, the schema was still growing.

**The breadth table.** For each [schema entry](../docs/terminology.md#3-schemas), how many maintainers' texts it was found in: 1, 2, or 3 or more. A schema entry found in one maintainer's texts only is that maintainer's own vocabulary; many such suggest the maintainers 040 doesn't read have their own too.

**Source.** It is ecology's sample-based rarefaction curve, the expected sample-based species accumulation curve over all orders of the samples, which judges whether a survey has found most species: a text plays the part of a sample, a schema entry that of a species (Gotelli & Colwell 2011, "Estimating species richness", in Magurran & McGill (eds), *Biological Diversity: Frontiers in Measurement and Assessment*, ch. 4: the curve is "the statistical expectation of the (sample-based) species accumulation curve" over the orders of the samples). The same idea, "saturation", decides how many interviews are enough in qualitative research (Guest, Bunce & Johnson 2006, "How Many Interviews Are Enough? An Experiment with Data Saturation and Variability", *Field Methods* 18(1), 59–82, [paper](https://doi.org/10.1177/1525822X05279903): new codes tracked after each set of six interviews; 92% of all codes had appeared by twelve). In [knowledge graph](../docs/terminology.md#8-the-pipeline) work, GrOIL (Mridul, Talukder & Seneviratne, "GrOIL: Graph-Grounded Domain Ontology Induction with Constrained LLM Mediation", 2026, arXiv:2608.22135v1, [paper](https://arxiv.org/abs/2608.22135v1), section 4.6) tracks how its ontology grows as documents are added, in one order. Averaging over every order, with a minimum support, to judge a schema-induction sample is this project's application of the ecology method; no knowledge graph paper found does that.

**Limits.** It is descriptive: it gives no verdict and no test, and where to call the curve flat is a judgment. It speaks only for what the sample was drawn from (by default 8 texts from each of the 19 strata of the pool, so a small stratum weighs as much as a large one), and within "(small maintainers)" only for the few of its 404 maintainers whose texts were drawn; the breadth table is only a hint about the others. It is slightly optimistic: it uses the labels 040 chose with every text in view, and a smaller sample might have labeled a few [component instances](../docs/terminology.md#2-triples) differently. It counts schema entries by support alone, before the check that leaves out schema entries the model judged too vague. Whether a bigger or wider sample makes extraction better is a question for the evaluation (`helpers/compare_runs.md`), not for this curve.

| `define_predicates.txt` | stage 7, 40 per call | write one defining sentence per predicate, or say it's too vague; it is shown each predicate's patterns and the entity classes being defined, which a definition may name (optional, except that a [pinned predicate](../docs/terminology.md#3-schemas)'s definition must name the entity classes of its pin, sent as `must_name`) |

Each prompt is a plain text file: open it to read exactly what the [model](../docs/terminology.md#8-the-pipeline) is told. `$name` marks where the code fills something in. Every prompt but `extract.txt` starts with a WORDS section, which defines each term the prompt uses, and each term those definitions use, in the same words in every prompt (`common/common_prompts/words.txt`, chosen by code: `common/common_helpers/prompt_files.py`, `words_for`); a term the extraction rules also define is worded as there (`tests/test_parallel.py`, *Words*). `extract.txt` carries the extraction rules, whose own section defines their words. No prompt uses "thing" or "kind" in their plain sense. Editing a prompt is allowed: the next [run](../docs/terminology.md#8-the-pipeline) asks again every call that uses it, and pays for them.

## Checks and warnings

Messages several steps share are in [`docs/running_on_nasa_laptop.md`, section 7, *Shared warnings and stops*](../docs/running_on_nasa_laptop.md#shared-warnings-and-stops); below are this step's own.

**Shown before paying**, above the confirmation question (and also in the [report](../docs/terminology.md#8-the-pipeline)'s warnings):

| Message | Meaning | What to do |
|---|---|---|
| *You asked for N texts from each stratum (texts_per_stratum), but M stratum(s) have fewer induction candidates that aren't twins of a text already drawn* | Those strata have fewer records to learn from than asked for, once twins of texts already drawn are skipped, so fewer texts are used (each stratum's count is in the report (`outputs/reports/040_induce_schema_<date>_<time>.md`), section *Results*, subsection *What this run worked on*). | Nothing, or lower `texts_per_stratum` to the number the message gives, to take the same number from every stratum. |
| *N maintainer(s) with induction candidates aren't named in annotations/ground_truth_candidates.json (the pool's design), so 040 counts them with the stratum "(small maintainers)"* | They joined the catalog, or changed their name, after the pool was drawn (2026-09-21), so the pool's design gives them no stratum. | Nothing if they are small; the report lists every stratum. |

**In the report**, under *Warnings*:

| Message | Meaning | What to do |
|---|---|---|
| *N record(s) failed: a model call for one of their text pieces failed, so each is left out of the evidence whole* | A [model call](../docs/terminology.md#8-the-pipeline) for a [text piece](../docs/terminology.md#1-records-and-their-text) of those records failed (after the model client's own retries), so each is left out whole, never half counted. The report gives each record's id and why, and its section *Records left out* counts them by reason (refused by the service's filter or by the model in prose, cut off at the answer length limit or, through Ask Sage, at the model's own limit, malformed reply, service error, other) and by maintainer, so it shows if they cluster in one maintainer (`common/common_helpers/dropped.py`, shared by 040, 050, 060 and 070). | Run the step again: only the failed pieces are asked again, and every answer already paid for is reused. An answer cut off at the length limit isn't asked again with the same settings: first change the setting the warning names (`docs/running_on_nasa_laptop.md`, section 7). Each failed call is described in `outputs/logs/<run id>_failed_calls.jsonl`. |
| *The service refused to answer about N item(s), even asked alone* | The model's service withheld its answer for these [component instances](../docs/terminology.md#2-triples) (stage 3), predicates (stage 5), or schema entries (stage 7): asked alone, each got one of these, all of them: a refusal that won't fix itself (an HTTP status of 400 or more that isn't retried), a refusal (its content filter's `finish_reason`, e.g. `content_filter`, or an answer in prose declining the task), no usable answer, an answer cut off (at `MAX_ANSWER_TOKENS`, or, through Ask Sage, at the model's own limit), no answer within `READ_TIMEOUT`, or an answer that twice wasn't JSON of the shape asked for. Any other failure (a rate limit or server error still failing after the retries, a lost connection) fails the step instead. Each batch it refused was asked again in halves, down to single items (`ask_split` in `common/common_helpers/cache.py`), so only these are missing: a refused component instance stays unlabeled, a refused predicate isn't split, a refused [schema entry](../docs/terminology.md#3-schemas) gets no definition. | Nothing if few. Each is in `induction_evidence.json` under `refused`, and what the model wrote before the stop is in the run's log (DEBUG lines starting "answer stopped by the service"). If many, try another model (`--model`). |
| *N texts gave no verified triple instance* | The model found none, or none it listed could be verified in the text. | Look at the texts and their `unverified` list in the [evidence](../docs/terminology.md#5-learning-the-schema-step-040) file; usually very short records. |
| *N component instances were left unlabeled even after a second try* | The model skipped them twice. They count toward no schema entry. | Nothing, if few. Listed in `induction_evidence.json` under `unlabeled`. |
| *The merge reply had items code ignored* | The model proposed a merge into something that isn't a [label](../docs/terminology.md#5-learning-the-schema-step-040), named labels it wasn't sent, merged a label twice, or merged a label into one already merged into it (a cycle: A into B, then B into A). Each time the first merge is kept. How they relate: a merge into something that isn't a label is skipped whole, so its labels aren't checked; each label of another merge counts under the first of the other three that applies, in this order (`not_sent`, `merged_twice`, `cycle`). Skipped without being counted: an item of the reply that isn't a JSON object, an item whose `labels` isn't a list, and a label merged into itself. | Nothing: they were ignored. Listed in `induction_evidence.json` under `merge_issues`, by kind: `into_not_a_label`, `not_sent`, `merged_twice`, `cycle` (in the order of this row's four cases). |
| *The splitting replies had N predicate split(s) code rejected* | A [predicate split](../docs/terminology.md#5-learning-the-schema-step-040) the model proposed (stage 5) failed one of the code checks (*How it works*, stage 5: not a JSON object, a predicate that wasn't sent, no new predicate, the name of a predicate found or of an earlier split, no grouping or another grouping than the predicate's earlier splits, no group, a group not the predicate's or already taken by an earlier split, every group of the predicate, or fewer supporting texts than `min_split_texts`). Its predicate stays as it was. | Nothing. Each is listed, with why, in the report's section *Splitting* and in `induction_evidence.json` under `splits`, `rejected`. |
| *N predicate split(s) passed every check but were left out because the predicate splits kept already add max_new_predicates (M) predicates* | The cap (*Settings*, `max_new_predicates`) was reached; the predicate splits with the fewest supporting texts were dropped, and their predicates keep those [triple instances](../docs/terminology.md#2-triples). | Nothing, or raise `--max_new_predicates`, weighing the longer step 060 prompt (the report's section *Splitting* gives by how much). |
| *N schema entries have no definition* | The model didn't define them, even when asked once more. They stay in the [schema](../docs/terminology.md#3-schemas), marked. | To ask again, delete `outputs/intermediate_results/040_induce_schema/cache/define.json`, then run `py 040_induce_schema/run.py` again. |
| *The definition replies named N schema entries that weren't sent* | Ignored. | Nothing. Listed under `unknown_schema_entries`. |
| *N definition(s) name a word shaped like an entity class (CamelCase) that is no entity class of this schema, even when asked once more* | Stage 7's check (*How it works*, stage 7): each definition is kept as written. | Read each: a proper noun (a place) is fine; a word meant as an [entity class](../docs/terminology.md#3-schemas) names none of this schema, so a model reading the definition in step 060 may look for one that isn't there. Listed under `definitions_naming_no_entity_class`. |
| *N definition(s) of a pinned predicate (a new predicate of a predicate split, stage 5) don't name every entity class its pin allows, even when asked once more* | Stage 7's check (*How it works*, stage 7). No prompt shows a pin, so a model reading the schema in step 060 learns it only from the definition; step 060 flags each triple that breaks the pin (`pattern_not_pinned`). Each definition and pin is kept. | Nothing, if few. To ask again, delete `outputs/intermediate_results/040_induce_schema/cache/define.json` (every definition is asked again), then run `py 040_induce_schema/run.py` again. Listed under `definitions_not_naming_their_pin`. |
| *N of M entity classes (or predicates, or patterns) have no origin, so they can't be traced to the input they came from* | Should never happen: a code change dropped the field that records where each item came from. | Fix the code before using the output. |

**The step stops** with:

| Message | Meaning | What to do |
|---|---|---|
| *… labels are more than one call takes* | Over 800 labels of one [kind](../docs/terminology.md#3-schemas): too many to merge in one call. | Learn from fewer texts (lower `--texts_per_stratum`), then run `py 040_induce_schema/run.py` again (see *Known limits*). |
| *… predicates after splitting are more than one call takes* | Over 800 predicates after splitting (stage 5): too many to merge again in one call. | Lower `--max_new_predicates` or learn from fewer texts (lower `--texts_per_stratum`), then run `py 040_induce_schema/run.py` again. |
| *missing input files, so the step can't run:*, then one line per missing file, e.g. *records: … (run `py 020_clean/run.py` first, or give another file with --records)*, or *ground_truth_schema: … (give the file with --ground_truth_schema)* | An input file isn't there: usually an earlier step hasn't run. | Run the steps in order, or pass the file with `--<input>`. |
| *The setting … must be …, but is …* | A [setting](../docs/terminology.md#8-the-pipeline) is outside its rule (`SPECS` in `040_induce_schema_helpers/texts.py`): `texts_per_stratum` and `min_support` a whole number from 1 to 10,000; `max_new_predicates` from 0 to 10,000; `min_split_texts` from 1 to 10,000; `workers` from 1 to 64; `max_chars` from 1,000 to 1,000,000; `repeat` from 1 on; `service`, `thinking` one of their values; `model` not empty; `confirm_paid_calls` true or false (`docs/running_on_nasa_laptop.md`, section 4). | *--texts_per_maintainer (or --induction_maintainers) was a setting of step 040's earlier sample design* (exit code 2) | The run was given a setting of the design the schema of 2026-10-12 was made with (the first `texts_per_maintainer` [induction candidates](../docs/terminology.md#4-ground-truth-and-samples) of each of the `induction_maintainers` largest maintainers). Since 2026-11-14, stage 1 draws by stratum instead, so the run stops before anything is read rather than mix the two designs up. | Run with `--texts_per_stratum <n>` instead (default 8). |
| *… doesn't describe the pool's strata as 040 reads them* | The `pool_design` file lacks a `places_per_stratum` object naming every stratum, "(small maintainers)" among them, a `strata` count equal to their number, or a `collapsed_maintainers` list. | Give the pool's design file with `--pool_design` (by default `annotations/ground_truth_candidates.json`, the file the pool was drawn with). |
| *… doesn't record the seed 030 drew its induction candidates' order with* | `splits.json` has no `drawn`, `settings`, `induction_seed`, which orders "(small maintainers)" and the reading order. | Delete 030's `splits.json`, run `py 030_split/run.py`, then run `py 040_induce_schema/run.py` again. |
| *Induction candidate … is not in 020's records (…): … and the records are out of step* | `splits.json` and 020's records don't agree, for example because 020 was rerun on a different [harvest](../docs/terminology.md#1-records-and-their-text) after 030 wrote `splits.json` (every cause: `docs/running_on_nasa_laptop.md`, section 7, *… not in 020's records …*). | Delete 030's `splits.json`, then run `py 030_split/run.py` (it writes the file only once), then run `py 040_induce_schema/run.py` again. |

## Audit trail

- **Prompts.** The [report](../docs/terminology.md#8-the-pipeline)'s *Prompts* section lists every prompt the [run](../docs/terminology.md#8-the-pipeline) filled in, each with a [fingerprint](../docs/terminology.md#8-the-pipeline) (sha256) of its exact text, so the prompt behind any answer is known even if the prompt file was edited later (`_manifest.json` keeps the full fingerprints).
- **[Log](../docs/terminology.md#8-the-pipeline).** `outputs/logs/<run id>.log` records the command line, the [settings](../docs/terminology.md#8-the-pipeline), the git commit, every [model call](../docs/terminology.md#8-the-pipeline)'s retries, each [move](../docs/terminology.md#8-the-pipeline)'s duration, each output file's hash and, on failure, the full traceback.
- **[Origin](../docs/terminology.md#8-the-pipeline).** Each [schema entry](../docs/terminology.md#3-schemas)'s `_origin` names the 020 [records](../docs/terminology.md#1-records-and-their-text) whose [texts](../docs/terminology.md#1-records-and-their-text) it was found in, e.g. `020_clean/records.jsonl#a1b2…`; `induction_evidence.json` keeps every text's [triple instances](../docs/terminology.md#2-triples) and [labels](../docs/terminology.md#5-learning-the-schema-step-040).
- **Trace.** `py helpers/audit.py <record id>` follows a record back through every [step](../docs/terminology.md#8-the-pipeline)'s output to the 010 [batch file](../docs/terminology.md#1-records-and-their-text) and the API request that first returned it (`helpers/audit.md`). An [entity class](../docs/terminology.md#3-schemas) or a [predicate](../docs/terminology.md#3-schemas) of the [schema](../docs/terminology.md#3-schemas) can be traced too: `py helpers/audit.py Instrument`. Why a predicate is or isn't in the schema: `py helpers/audit.py --induction "aboard|on board"` shows every triple instance with those words, its label, the merges, the [spelling fold](../docs/terminology.md#3-schemas), the [predicate split](../docs/terminology.md#5-learning-the-schema-step-040) its subject's or object's entity class or its pattern put it in, the predicate merging again made of it, and whether its predicate is in the schema or deferred (`helpers/audit.md`, *Tracing what step 040 did with a predicate*).

## Known limits

- **Run with the real [model](../docs/terminology.md#8-the-pipeline) since 2026-10-12** (`claude-opus-5.5` through LiteLLM, the schema of 2026-10-12 included, which was made with the earlier sample design: the first 15 [induction candidates](../docs/terminology.md#4-ground-truth-and-samples) of each of the 10 largest maintainers, the settings `induction_maintainers` and `texts_per_maintainer`, replaced on 2026-11-14 by the draw by stratum, and without the [source text](../docs/terminology.md#1-records-and-their-text) in labeling or splitting; that schema, `docs/induced_schema.json`, keeps those settings under `made`: that spelling was the default until 2026-11-01, when it became `claude-opus-5-5`, the same name as LiteLLM lists it; `docs/findings.md`, 2026-11-01). What those runs measured, including how much the schema varies from [run](../docs/terminology.md#8-the-pipeline) to run, is in `docs/findings.md`.
- **Adding [texts](../docs/terminology.md#1-records-and-their-text) relabels.** Taking more texts reuses every extraction already made, but labeling ([stage](../docs/terminology.md#8-the-pipeline) 3), merging (4), splitting (5), and definitions (7) are asked again when the set of [component instances](../docs/terminology.md#2-triples) changes: each labeling batch depends on the [labels](../docs/terminology.md#5-learning-the-schema-step-040) chosen before it. That's a few dozen [model calls](../docs/terminology.md#8-the-pipeline), not one per text.
- **The labels depend a little on the order component instances are labeled in.** Most common first, so the order is meaningful, not arbitrary, but a different order could coin a different first label for an idea.
- **One call per [kind](../docs/terminology.md#3-schemas) to merge labels.** Up to 800 labels of one kind; above that the [step](../docs/terminology.md#8-the-pipeline) stops rather than merging in groups where synonyms could miss each other. At that size, labels would first need grouping by meaning (e.g. a local embedding model), which isn't built.
- **The sample weighs every stratum the same.** Equal allocation suits discovery, not estimation: a [schema entry](../docs/terminology.md#3-schemas)'s support counts texts of a sample in which the smallest stratum (81 records) has as many texts as the largest (10,650 records), so support is no estimate of how common the entry is in the catalog. Within "(small maintainers)", 8 texts stand for 404 maintainers (2,082 records), so an [entity class](../docs/terminology.md#3-schemas) or predicate used only by some of them is likely missed. 070's [recall upper bound](../070_evaluate/metrics/recall_upper_bound.md) shows whether what was missed matters for the [ground truth](../docs/terminology.md#4-ground-truth-and-samples). The design (8 texts per stratum) is a chosen starting point, not a measured optimum; read *Saturation* to judge it, and compare other designs with it (`helpers/compare_runs.md`).
- **Only exact twins are skipped.** Stage 1 skips a text whose `notes`, [evened out](../docs/terminology.md#2-triples), are those of a text already drawn (whole-text and notes-only twins). A near-duplicate (the same `notes` but for a granule number or a date) is drawn, and a schema entry found in both counts twice. Skipping near-duplicates would need a similarity measure and a threshold to choose and justify; exact twins need neither, are defined once for the whole pipeline (`common/common_helpers/ground_truth.py`, `twin_kinds`), and their skips are counted per stratum, so a later near-duplicate rule can be compared with them. With `min_support` 1, support decides nothing, so a near-duplicate adds no schema entry a single copy wouldn't.
- **Splitting rests on the model's judgment and on the labels.** The model decides which predicates stand for different relationships; code checks only that each [predicate split](../docs/terminology.md#5-learning-the-schema-step-040) is well formed (*How it works*, stage 5). A predicate is split by one grouping per run (subject, object or pattern), and a mislabeled [subject instance](../docs/terminology.md#2-triples) or [object instance](../docs/terminology.md#2-triples) (stage 3) lands in the wrong split. A split whose parts merging again merges back into one predicate is undone, never kept as a renaming. `min_split_texts` (2) is a chosen bound, not a measured one (*Settings*). `max_new_predicates` (50) is a chosen bound on the step 060 prompt's growth, not a measured optimum (*Settings*).
- **min_support is not yet chosen.** It is 1 (keep everything). To choose it: run 040, 060, and 070 with other values and compare the **[tuning part](../docs/terminology.md#7-evaluating-extraction-step-070)'s** metrics, never the [held-out part](../docs/terminology.md#7-evaluating-extraction-step-070)'s (see `070_evaluate/070_evaluate.md`). How to weigh [precision](../docs/terminology.md#7-evaluating-extraction-step-070) against [recall](../docs/terminology.md#7-evaluating-extraction-step-070) when choosing is still open.
- **[Shared-model bias](../docs/terminology.md#7-evaluating-extraction-step-070).** By default 040 induces the schema with the model 060 extracts with (`claude-opus-5-5`), and 070's proposed rows of the [translation table](../docs/terminology.md#7-evaluating-extraction-step-070) come from it too; every number is then that of a schema and an extraction from one model, and a row kept because it was proposed moves [schema fit](../docs/terminology.md#7-evaluating-extraction-step-070) and reach: `070_evaluate/070_evaluate.md`, [*Shared-model bias*](../070_evaluate/070_evaluate.md#shared-model-bias).
- **The model varies.** Rerunning with an empty cache can give different [triple instances](../docs/terminology.md#2-triples), labels, and definitions; the cache is what makes a rerun reproducible.
