## Records and fields

Throughout this project, a "[record](docs/terminology.md#1-records-and-their-text)" is the metadata of one catalog entry in <[data.nasa.gov](https://data.nasa.gov)>. In JSON terms, each record is one object with 31 possible top-level key-value pairs, of which 24 are populated at least once across the catalog (in the [harvest](docs/terminology.md#1-records-and-their-text) of 2026-10-01; title, `notes`, [maintainer](docs/terminology.md#1-records-and-their-text), tags, and so on; the other 7 are empty on every record). Being metadata, the records describe the catalog entries; any actual scientific data or content lives in separate NASA data archives that each record links to, and is never downloaded here. Most catalog entries of data.nasa.gov are datasets.
The keys of these top-level key-value pairs are what we call [metadata fields](docs/terminology.md#1-records-and-their-text) or just [fields](docs/terminology.md#1-records-and-their-text). Fields come from the raw JSON in which data.nasa.gov's public API returns each record. The API returns every record with the same metadata form provided by CKAN, a standard open-source catalog software, which data.nasa.gov runs on. The data.nasa.gov website renders each record as a readable page (headline, description [text](docs/terminology.md#1-records-and-their-text), tag buttons), but the harvest in this project comes from the API, which is why we know the exact name (top-level key) and the exact populated content (the value of that key) of each field of a record, rather than guessing either from webpage text.

An example of a real record can be seen by opening the following link in a browser (ticking off the pretty-print box at the top is advised):<https://data.nasa.gov/api/3/action/package_search?rows=1>. You can see field names that exist in every record, like `id`, `title`, `notes`, `maintainer`, `organization`, `tags`, `resources`, `extras`, etc., as well as the populated contents of each field, which are particular to this record. Several fields hold nested objects and arrays that have fields of their own: `organization` is an object with ~7 inner keys, `tags` is an array where each of its entries has ~4 inner keys, `resources` is an array where each of its entries has ~15 inner keys, and `extras` is a (currently unexplored!) array of extra key-value pairs. Our census counted at the top level, then reached one level deeper only where the design needed it (`tags[].name`, `resources[].format`, `organization.title`). The inner-key counts are approximate because we never censused the nested layers, only the three aforementioned inner keys the design actually reads.

**A note on timing:** the catalog itself is not static! A handful of records is added every week, so any harvest is a snapshot of a specific date. The phase 1 graph was built from a harvest taken 2026-08-30 (36,289 records); a re-harvest on 2026-09-02 returned 36,323. We take care to note the date on which a harvest was taken whenever counts are involved in this README.

## Project phases

There are two phases to the building of this [knowledge graph](docs/terminology.md#8-the-pipeline). Phase 1 turned the metadata [fields](docs/terminology.md#1-records-and-their-text) other than the [text fields](docs/terminology.md#1-records-and-their-text), such as `maintainer`, of every [record](docs/terminology.md#1-records-and-their-text) into edges of the graph; phase 2, still in progress, extracts facts from the text fields, such as `title` (title of catalog entry) and `notes` (explanation of catalog entry). Phase 1 is mostly complete, and its [schema](docs/terminology.md#3-schemas) is summarized in the table below:

| Node label | Count | From | Properties | Relationship to Dataset |
|---|---:|---|---|---|
| Dataset | 36,289 | one per record | id, name, title, created, modified, license | |
| Maintainer | 434 | `maintainer` field | name | `(Dataset)-[:MAINTAINED_BY]->(Maintainer)` |
| Keyword | 8,277 | `tags`, cleaned | name | `(Dataset)-[:TAGGED_WITH]->(Keyword)` |
| Format | 63 | `resources[].format` | name | `(Dataset)-[:AVAILABLE_AS]->(Format)` |


## Phase 1: how the census decided the design

A data census (`archive/to_be_reshaped/nasa_census.py`) is what decided this design. This script counted, for every [field](docs/terminology.md#1-records-and-their-text), how often it is filled and how many distinct values it holds. Those counts decided whether and what each field becomes in the [knowledge graph](docs/terminology.md#8-the-pipeline):

- If many [records](docs/terminology.md#1-records-and-their-text) share a field's values and those values are worth traversing through, the values become [nodes](docs/terminology.md#8-the-pipeline). If a field fails that test but its values still answer some question by filtering or identifying (license, title, dates), the values become properties.
- If a field's values answer no question anyone would ask the graph (`creator_user_id`, `isopen`), the field is ignored.
- Values that mean "empty" become nothing, whatever their field.

These decisions work because of convergence, meaning many different records mentioning the same value. When a value converges, such as 6,214 records sharing the [maintainer](docs/terminology.md#1-records-and-their-text) "Planetary Data System", storing it as one node attaches all 6,214 [edges](docs/terminology.md#8-the-pipeline) to it, and standing on that node answers "everything connected to this value" in one hop. A value only one record names would yield a node with a single edge, connecting nothing to nothing, so non-converging values stay properties.

This node-versus-property criterion is my own; I found no published source for it. The criterion also involves judgment, not just counting: `license_title` has only 4 distinct values shared across thousands of records, but nobody would traverse from license to license, only filter by it, so per the first bullet it stays a [property](docs/terminology.md#8-the-pipeline).

Each field's numbers then forced a decision:

- `organization` has 1 distinct value across all records ("NASA"), which connects everything to everything and therefore means nothing, so it is ignored.
- `maintainer` has 435 distinct values that are heavily shared, so it became the `Maintainer` label and the `MAINTAINED_BY` [relationship type](docs/terminology.md#8-the-pipeline). Its value "undefined" (989 records) means empty and produces no relationship.
- `tags` has 8,279 distinct values with 132k total uses, so it became the `Keyword` label and `TAGGED_WITH`. Its junk values "__" (7,673 uses) and "nasa" (1,086 uses) produce no nodes.
- `resources[].format` has 63 distinct, heavily shared values, so it became the `Format` label and `AVAILABLE_AS`. Resources exist on only 54.9% of records, so a dataset with no formats is normal, not an error.
- `license_title` has only 4 distinct values. You would filter on it, never traverse through it, so it stays a property on `Dataset`.
- `id`, `name`, `title`, and the timestamps are unique per record, so they stay properties on `Dataset`.
- `notes` is 100% filled with a median of 529 characters of prose, which code cannot parse, so it is reserved for phase 2.
- The remaining administrative fields (`creator_user_id`, `isopen`, `state`, `owner_org`, `private`, `type`, `tracking_summary`, and similar) are populated but answer no question anyone would ask the graph, so they are ignored.
- `extras` is not ignored but deferred: it holds a grab-bag of additional key-value pairs (a look at one record showed entries like publisher and time coverage), and we might explore it further down the line.
- 7 fields (`author`, `author_email`, `groups`, `relationships_as_subject`, `relationships_as_object`, `url`, `version`) exist on every record but are populated on none, so there is nothing to decide about them.

Only three nested fields got a deeper look: `tags[].name`, `resources[].format`, and `organization.title`. Digging into a nested field only pays off if it might contain values shared across records, since only shared values can become nodes, and these three are the only nested fields where that is possible. The other nested fields hold view counts (unique numbers per record) or are empty on every record, and `extras` was consciously deferred, as noted above. Within each of the three, we read the one inner key that names the thing (`name`, `format`, `title`) and skipped the keys that administer it (ids, states, sizes, timestamps).

Phase 1 made edges from what can be read directly from the [metadata fields](docs/terminology.md#1-records-and-their-text) other than the [text fields](docs/terminology.md#1-records-and-their-text): once again, no interpretation is needed so code just copies each field value directly. Phase 2 extracts [facts](docs/terminology.md#2-triples) from the natural-language prose in each record's `notes` and `title` fields, which requires actually reading the [text](docs/terminology.md#1-records-and-their-text), so a large language [model](docs/terminology.md#8-the-pipeline) processes this text and code checks its output.

## Phase 2: extracting facts from text (work in progress)

> Phase 2 is not part of the polished deliverable yet.

Phase 2 mines the text [fields](docs/terminology.md#1-records-and-their-text) (`notes` and `title`) of each [record](docs/terminology.md#1-records-and-their-text), which is where the interesting [facts](docs/terminology.md#2-triples) hide: which instrument took the data, aboard which spacecraft, observing what, measuring what.

Where phase 1 merely copied field values, phase 2 has to extract facts from prose, so the work splits into three questions: what [schema](docs/terminology.md#3-schemas) (which [entity classes](docs/terminology.md#3-schemas) and predicates) should the facts use, how do we get the facts out, and how do we know whether they are right.

### Harvest (step 010)

Everything starts from one download of the whole catalog through data.nasa.gov's public API: the metadata only (titles, `notes` fields, [maintainers](docs/terminology.md#1-records-and-their-text), tags, formats, links), never the scientific data the [records](docs/terminology.md#1-records-and-their-text) point to. A [harvest](docs/terminology.md#1-records-and-their-text) is a snapshot of the catalog on the day it was taken, and the date travels with every later result. Pages are fetched in a fixed order (oldest record first), so records added or edited during the harvest can't shift the pages; each page is saved as it arrives, so an interrupted harvest resumes where it stopped; and each page keeps the request that returned it, which is where every record's history starts.

Details: [`010_harvest/010_harvest.md`](010_harvest/010_harvest.md).

### Cleaning (step 020)

The `notes` and `title` [fields](docs/terminology.md#1-records-and-their-text) are cleaned before anything reads them. In the [harvest](docs/terminology.md#1-records-and-their-text) of 2026-10-01, 1,276 of 36,406 `notes` fields and 6 titles carried HTML markup baked into the [text](docs/terminology.md#1-records-and-their-text) (escaped tags, sometimes escaped twice), which would otherwise produce [triple instances](docs/terminology.md#2-triples) and [classed triples](docs/terminology.md#2-triples) about paragraph tags rather than about datasets. The cleaner verifies its own work: every word, number, and URL fragment in the source must survive into the cleaned value, and a value that would lose content falls back to a cruder method or to the uncleaned value itself. In that harvest, 2 `notes` fields needed a fallback and none lost content. Titles are also made one line: 3,361 had line breaks or runs of spaces inside, which the website hides but a file keeps. The cleaned [records](docs/terminology.md#1-records-and-their-text) are written to `records.jsonl` ([step](docs/terminology.md#8-the-pipeline) 020), one per line, each field under its own key.

The same step also joins [maintainer](docs/terminology.md#1-records-and-their-text) spellings, e.g. "Kristan Morgan" and "KRISTAN MORGAN" are one person; left apart they count as two communities everywhere downstream. Spellings matching once case, punctuation, word order, and titles (Dr., Ph.D.) are ignored are treated as one, which took the 434 spellings in the harvest of 2026-09-27 down to 422 maintainers. Spellings differing by a middle initial are left apart, since joining those needs a rule nobody has chosen.

Details: [`020_clean/020_clean.md`](020_clean/020_clean.md).

### Splitting (step 030): two samples that never overlap

Two parts of the work need [records](docs/terminology.md#1-records-and-their-text) to read: learning the [schema](docs/terminology.md#3-schemas), and the [ground truth](docs/terminology.md#4-ground-truth-and-samples) that judges extraction. They must never share a record. If the schema were learned from the same records it is later judged on, the records judging it would have shaped it, and its metrics would look better than it is. So [step](docs/terminology.md#8-the-pipeline) 030 keeps them apart:

- the **[ground truth candidates pool](docs/terminology.md#4-ground-truth-and-samples)**: 1,000 records drawn once, on 2026-09-21, from 36,323 records (the count the harvest of 2026-09-02 returned; `ground_truth_candidates.json` doesn't name the harvest), in a shuffled order (below); 999 were still in the catalog in the [harvest](docs/terminology.md#1-records-and-their-text) of 2026-10-01;
- the **[induction candidates](docs/terminology.md#4-ground-truth-and-samples)**: every other record with [text](docs/terminology.md#1-records-and-their-text) (35,407 in the harvest of 2026-10-01), each [maintainer](docs/terminology.md#1-records-and-their-text)'s in a fixed random order.

Both orders are fixed, so taking more records later keeps the ones already taken: any first *k* records of the pool are a [fair sample](docs/terminology.md#4-ground-truth-and-samples) of the catalog, and any first *k* of a maintainer's induction candidates are a random sample of that maintainer's records.

030 also splits the [pool](docs/terminology.md#4-ground-truth-and-samples) into a **[tuning part](docs/terminology.md#7-evaluating-extraction-step-070)** and a **[held-out part](docs/terminology.md#7-evaluating-extraction-step-070)** for evaluation (step 070). While improving the pipeline, only the tuning part's metrics are looked at; the held-out part's metrics are looked at only at the end, and that is the number reported. Otherwise the pipeline would get tuned to the very records it is evaluated on, and its metrics would flatter it. From [pool position](docs/terminology.md#4-ground-truth-and-samples) 6 on, every third record is held out; positions 0–5, from which the [ground truth schema](docs/terminology.md#3-schemas) was written, are tuning.

Details: [`030_split/030_split.md`](030_split/030_split.md).

### Schema induction (step 040)

The [schema](docs/terminology.md#3-schemas) is derived from the catalog rather than written in advance. The data-driven method to induce the schema follows AutoSchemaKG ([arXiv:2505.23628](https://arxiv.org/abs/2505.23628)): take a sample of [records](docs/terminology.md#1-records-and-their-text) (the first 15 [induction candidates](docs/terminology.md#4-ground-truth-and-samples) of each of the 10 largest [maintainers](docs/terminology.md#1-records-and-their-text), who together held 91.6% of the catalog's records in the [harvest](docs/terminology.md#1-records-and-their-text) of 2026-10-01), extract [triple instances](docs/terminology.md#2-triples) with no schema imposed, give every [component instance](docs/terminology.md#2-triples) a general [label](docs/terminology.md#5-learning-the-schema-step-040), merge the labels that mean one thing, and count how many distinct records produced each [schema entry](docs/terminology.md#3-schemas) found. The [model](docs/terminology.md#8-the-pipeline) also names each record's [describes class](docs/terminology.md#2-triples) (e.g. Dataset, WebTool, Document), so the schema always has those [entity classes](docs/terminology.md#3-schemas). Every schema entry found is kept with its [evidence](docs/terminology.md#5-learning-the-schema-step-040); a cutoff, to be chosen from [step](docs/terminology.md#8-the-pipeline) 070's metrics, decides which enter the schema (today the cutoff is 1 record, so every schema entry found enters except those the model finds too vague to define, and the [patterns](docs/terminology.md#3-schemas) that use them). [Support](docs/terminology.md#5-learning-the-schema-step-040) is counted in distinct texts (one per record), and each schema entry also records how many maintainers' texts it was found in, so a pattern backed by one maintainer's house style is visible as such rather than passing as a catalog-wide regularity. What code can check, it checks rather than trusting the model: each triple instance's [source text](docs/terminology.md#1-records-and-their-text) must really be in its record's [text](docs/terminology.md#1-records-and-their-text), or the triple instance isn't counted, and the counts, the patterns' entity classes, and each entity class's examples are computed by code.

Details: [`040_induce_schema/040_induce_schema.md`](040_induce_schema/040_induce_schema.md).

### Annotation (step 050): the ground truth

None of the above says whether extraction is correct, and no query built on the graph is worth more than the extraction under it. Assessing quality needs [ground truth](docs/terminology.md#4-ground-truth-and-samples): [classed triples](docs/terminology.md#2-triples) a person corrects, [record](docs/terminology.md#1-records-and-their-text) by record (checked once the record is finished). The [ground truth candidates pool](docs/terminology.md#4-ground-truth-and-samples) is where they come from. They are candidates: only a subset will ever be annotated and used as ground truth, since verifying 1,000 records by hand is more than the time available.

The [pool](docs/terminology.md#4-ground-truth-and-samples) is a stratified random sample: records are grouped by [maintainer](docs/terminology.md#1-records-and-their-text) into [strata](docs/terminology.md#4-ground-truth-and-samples), each stratum gets places in proportion to its size (proportional allocation; its source: [`070_evaluate/metrics/approximately.md`, *Sources*](070_evaluate/metrics/approximately.md#sources)), maintainers too small to earn two places are combined into one stratum, and the records are shuffled so that the first k of them are a [fair sample](docs/terminology.md#4-ground-truth-and-samples) for any k. That last property is what makes partial annotation usable: annotation will stop long before 1,000, and wherever it stops, what has been annotated is still a fair sample rather than one biased by alphabetical or by-maintainer ordering. Records are therefore annotated in the pool's order; [step](docs/terminology.md#8-the-pipeline) 050 says when the ground truth stops being the first records of the pool.

Annotating is slow, and the rules had to be worked out on the records themselves. Each record gets one structural classed triple, the [describes triple](docs/terminology.md#2-triples), keeping the catalog entry separate from the thing it describes. The [entity classes](docs/terminology.md#3-schemas) and [predicates](docs/terminology.md#3-schemas) decided this way are kept in the [ground truth schema](docs/terminology.md#3-schemas) (`annotations/ground_truth_schema.txt`), which grows as annotation proceeds; it is small and elementary, and it is expected to keep growing.

Writing every classed triple by hand is the bottleneck, so step 050 drafts the classed triples of the next few records (10 per drafted batch by default), asking the [model](docs/terminology.md#8-the-pipeline) for every [fact](docs/terminology.md#2-triples) the [text](docs/terminology.md#1-records-and-their-text) states, in the ground truth schema's [component classes](docs/terminology.md#3-schemas) where they fit. A person then corrects each [drafted batch](docs/terminology.md#4-ground-truth-and-samples) in the [annotation tool](docs/terminology.md#4-ground-truth-and-samples) (`py helpers/annotate.py`), a page in the browser that shows each record's text with its classed triples and saves every change into `annotations/ground_truth/`. [Drafted triples](docs/terminology.md#4-ground-truth-and-samples) are not checked: a human keeps, edits, deletes, or adds, driven by the record's text. Two biases remain, since the ground truth starts as a model's drafted triples: keeping a wrong drafted triple is easy, and a fact the model missed is unlikely to be added. So any metric against this ground truth is reported as such: drafted by a model and corrected by a person, not written from scratch.

Details: [`050_annotate/050_annotate.md`](050_annotate/050_annotate.md).

### Extraction (step 060)

[Step](docs/terminology.md#8-the-pipeline) 060 extracts, from each [record](docs/terminology.md#1-records-and-their-text)'s [text](docs/terminology.md#1-records-and-their-text), only the [facts](docs/terminology.md#2-triples) the [schema](docs/terminology.md#3-schemas) can express, in only the schema's [component classes](docs/terminology.md#3-schemas). The [current schema](docs/terminology.md#6-extracting-with-a-schema-step-060) is, by default, 040's [induced schema](docs/terminology.md#5-learning-the-schema-step-040) plus the [schema additions](docs/terminology.md#3-schemas) ([entity classes](docs/terminology.md#3-schemas), [predicates](docs/terminology.md#3-schemas), and patterns a person writes in `annotations/schema_additions.txt`, e.g. on a mentor's advice, each noting where the idea came from); any other schema can be given instead. Code checks every [classed triple](docs/terminology.md#2-triples): one whose [source text](docs/terminology.md#1-records-and-their-text) isn't in the record's text (it may be invented), or that uses a component class the schema doesn't have, is removed with the reason; the rest are kept. The component classes outside the schema the [model](docs/terminology.md#8-the-pipeline) keeps reaching for are listed, as candidates for the schema additions. Until the schema is final, 060 extracts only from the finished [ground truth](docs/terminology.md#4-ground-truth-and-samples) records, which is all step 070 can evaluate; afterwards, from every record.

Details: [`060_extract/060_extract.md`](060_extract/060_extract.md).

### Evaluation (step 070)

With enough annotated [records](docs/terminology.md#1-records-and-their-text), extraction can be evaluated: **[precision](docs/terminology.md#7-evaluating-extraction-step-070)** is how often 060 is right when it says something, and **[recall](docs/terminology.md#7-evaluating-extraction-step-070)** is how many of the ground truth triples it found. The point of the exercise is not a single number but a fixed measuring stick: the same annotated records can be run against a different prompt, a different [model](docs/terminology.md#8-the-pipeline), or extraction with and without the [induced schema](docs/terminology.md#5-learning-the-schema-step-040), and the difference between those runs is what says whether any of them is worth its cost.

[Step](docs/terminology.md#8-the-pipeline) 070 first translates the [current schema](docs/terminology.md#6-extracting-with-a-schema-step-060)'s [component classes](docs/terminology.md#3-schemas) into the [ground truth schema](docs/terminology.md#3-schemas)'s, through the [translation table](docs/terminology.md#7-evaluating-extraction-step-070), which a person checks (`annotations/component_class_mapping.csv`). It then pairs each record's [occurrences](docs/terminology.md#7-evaluating-extraction-step-070) (its [translated extracted triples](docs/terminology.md#7-evaluating-extraction-step-070)) with its [ground truth triples](docs/terminology.md#4-ground-truth-and-samples), at two levels: **[exact pairs](070_evaluate/metrics/pairs.md)**, [subject instance](docs/terminology.md#2-triples) and [object instance](docs/terminology.md#2-triples) the same once [evened out](docs/terminology.md#2-triples), and **[partial pairs](070_evaluate/metrics/pairs.md)**, one containing the other ("MODIS" in "Moderate Resolution Imaging Spectroradiometer (MODIS)"); and it counts all pairs, and **strict** pairs, whose [subject classes](docs/terminology.md#2-triples) and [object classes](docs/terminology.md#2-triples) agree too. Beside precision and recall it reports the **[recall upper bound](docs/terminology.md#7-evaluating-extraction-step-070)**, how much of the [ground truth](docs/terminology.md#4-ground-truth-and-samples) the current [schema](docs/terminology.md#3-schemas) can express at all, so a weak schema and a weak extraction can be told apart; and, on its own, the [describes accuracy](docs/terminology.md#7-evaluating-extraction-step-070), how often 060 named each record's [describes class](docs/terminology.md#2-triples) right, next to the [describes baseline](docs/terminology.md#7-evaluating-extraction-step-070), what always guessing the most common one would get.

Every number comes with its **[margin of error](docs/terminology.md#7-evaluating-extraction-step-070)**, computed by redrawing whole records many times from all the [strata](docs/terminology.md#4-ground-truth-and-samples) together, not within each stratum (the [bootstrap](docs/terminology.md#7-evaluating-extraction-step-070)), which is only valid for a [fair sample](docs/terminology.md#4-ground-truth-and-samples) of enough records: 070 evaluates only the first records of each part of the [pool](docs/terminology.md#4-ground-truth-and-samples), in pool order and with none of the part skipped, and gives no margin below 20 of them. Only the **[tuning part](docs/terminology.md#7-evaluating-extraction-step-070)** of the ground truth is shown while the pipeline is being improved; the **[held-out part](docs/terminology.md#7-evaluating-extraction-step-070)** is looked at only at the end, and every look is logged, so the reported numbers don't flatter choices made by looking at them.

Details: [`070_evaluate/070_evaluate.md`](070_evaluate/070_evaluate.md).
