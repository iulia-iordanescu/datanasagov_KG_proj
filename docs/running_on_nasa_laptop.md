# Running the pipeline on the NASA laptop

The code is built and tested on a personal laptop, which can't reach NASA's LiteLLM or Ask Sage, the NASA services that reach the AI [model](terminology.md#8-the-pipeline). Real [runs](terminology.md#8-the-pipeline) happen on the NASA laptop, after pulling the code from GitHub. This page is the checklist for that. Items get added at the end as the pipeline grows.

Two things never travel through Git, on purpose:

- **`.env`**, which holds your service keys: a key in Git could be read by anyone who can see the repository.
- **`outputs/`**, everything a pipeline run produces: it's rebuilt by running the [steps](terminology.md#8-the-pipeline), and it's large.

So the NASA laptop needs its own `.env`, and makes its own `outputs/` by running the steps.

## 1. Get the code

In PowerShell, in the folder where the repository lives (or where you want it):

```powershell
git clone https://github.com/iulia-iordanescu/datanasagov_KG_proj.git     # first time only
cd datanasagov_KG_proj
git fetch
git switch main
git pull
```

The work is on the branch `main`.

If Git then shows many files as changed although you didn't touch them, that's the line-ending rule (`.gitattributes`) settling in. Run this once, then check that `git status` is clean:

```powershell
git add --renormalize .
git status
```

## 2. Set up Python

Follow `docs/virtual_environment_setup.md`, with one difference: **install from the saved package list rather than saving a new one.** In short, from the repository folder:

```powershell
py -3.14 -m venv .myvenv
.\.myvenv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

If PowerShell says running scripts is disabled, see part 3 of the setup guide.

Every new PowerShell window needs `.\.myvenv\Scripts\Activate.ps1` again; your prompt then starts with `(.myvenv)`.

## 3. Add your keys

Create the file `.env` with your service keys: part 6 of `docs/virtual_environment_setup.md`. NASA's LiteLLM (the default `service`, see *Choosing a model*) needs the line `LITELLM_API_KEY=sk-...`; Ask Sage needs your email and key. A LiteLLM key is made in LiteLLM's dashboard (https://proxy.fast.luna.nasa.gov/ui/, *Virtual Keys*, *Create New Key*; key type *AI APIs*; models left empty for all your team's models). LiteLLM shows the full key once: copy it into `.env` at once, and never into a chat or a file Git tracks.

## 4. Run the steps, in order

Each [step](terminology.md#8-the-pipeline) reads what the one before it wrote, so run them in this order. From the repository folder, with the environment active:

| Step | Command | Time (measured 2026-09-27/28) | Pays for model calls? |
|---|---|---|---|
| 010 [harvest](terminology.md#1-records-and-their-text) | `py 010_harvest/run.py` | about 23 min | no |
| 020 clean | `py 020_clean/run.py` | about 15 s | no |
| 030 split | `py 030_split/run.py` | about 3 s | no |
| 040 induce [schema](terminology.md#3-schemas) | `py 040_induce_schema/run.py` | not yet measured | **yes** |
| 050 annotate | `py 050_annotate/run.py` | not yet measured | **yes** (about one call per [record](terminology.md#1-records-and-their-text)) |
| 060 extract | `py 060_extract/run.py` | not yet measured | **yes** (about one call per record: by default only the finished [ground truth](terminology.md#4-ground-truth-and-samples) records) |
| 070 evaluate | `py 070_evaluate/run.py` | not yet measured | **yes**: two kinds of call, each only when needed: one call per 100 [component classes](terminology.md#3-schemas) of the [current schema](terminology.md#6-extracting-with-a-schema-step-060) not yet in `annotations/component_class_mapping.csv`, only when there are some (then check those rows and run it again); and, on a run that gets past the [translation table](terminology.md#7-evaluating-extraction-step-070), one call suggesting counterparts for the rows that say `(none)`, only when a row of the current schema says `(none)` while the [ground truth schema](terminology.md#3-schemas) has a component class of the same kind that nothing translates to (cached by the lists asked about, so the same lists are never paid for twice) |

Each step ends by printing where its [report](terminology.md#8-the-pipeline) is (`outputs/reports/<run id>.md`). Read the report's **Warnings** before running the next step. Each step's guide (`<step>/<step>.md`) says what every warning means and what to do.

**Or all in order:** `py run_pipeline.py` runs the steps above one after the other, each exactly as its command would (`--from 040`, `--to 060`, or `--only 070` for part of them). Each step that pays still asks before paying. It stops at the first step that doesn't finish; 050 drafts a new [drafted batch](terminology.md#4-ground-truth-and-samples) only when none is waiting for you to correct; 060 and 070 wait until the ground truth has a [finished record](terminology.md#4-ground-truth-and-samples). At the end it prints where its own report is (`outputs/reports/000_pipeline_<date>_<time>.md`): each step's status, headline numbers, warnings, and report, and what to do next. `py run_pipeline.py --status` shows what to do next at any time, running nothing (each item explained in `docs/upkeep.md`). For the test run (section 5), run the steps one by one: their tiny settings differ from step to step.

**How a step ends.** Each step ends with one of four statuses, given in its report (*Run*, *Status*) and its last line, each with its exit code: `ran` (0: it finished, and wrote its outputs and manifest), `stopped` (2: on purpose, for one of these, all of them: a check found a problem you can fix (each step's guide, *Checks and warnings*, lists its own; rows for you to check among them), a setting below its minimum or one the model calls can't use (`service`, `model`, `thinking`), a key missing from `.env`, the question before paying (or 070's question about its warnings) declined or its input closed, the [test call](terminology.md#8-the-pipeline) failed or was cut off, an input that changed while the step ran (its files are hashed at the start and checked again at the end: the [annotation tool](terminology.md#4-ground-truth-and-samples) saving a ground truth file while 070 waited at its question, a hand edit, another step; the outputs may mix old and new content, so no manifest is written: run the step again), or the early stop), `interrupted` (130: Ctrl+C, whenever you press it, during the [model calls](terminology.md#8-the-pipeline) and at the question before paying too; every answer already received is kept in the cache), or `failed` (1: an error, a missing input file among them). After any but `ran`, the run writes no manifest of its own, and the previous run's manifest is put back only if every output file it lists is unchanged. `run_pipeline.py`'s report gives each step one of these, or one of three more for a step it didn't start: `kept` (050, while a drafted batch waits for you), `skipped` (060 and 070, while the ground truth has no finished record), or `not run` (an earlier step didn't end `ran`, `kept`, or `skipped`). Its own exit code is 0, or the exit code of the first step that ended `stopped`, `interrupted`, or `failed`.

**Files and the console.** Every text file a step, a helper or the annotation tool reads goes through `common/common_helpers/files.py` (UTF-8; a byte-order mark, which Notepad or Excel may add, dropped; Windows line endings read as plain), and every file they write is UTF-8 with plain line endings (so hashes don't depend on the computer). A file that isn't UTF-8 (saved in the Windows code page by Excel, say) or isn't in its format (JSON, a JSON line, a CSV) stops the step with a message naming the file and the line (*… isn't UTF-8 text …*, *… isn't valid JSON (line N, column M …)*, *… line N isn't valid JSON …*, *… line N: not a record with an id …*), never a traceback. Every program a person runs (`run_pipeline.py`, each step, every `helpers/*.py`, `tests/run_all.py`) sets the console up first (`common/common_helpers/console.py`): a character the console or a redirected output can't encode (✖, →, in the cp1252 code page) is shown as `?` instead of ending the program with `UnicodeEncodeError`.

### Settings several steps share

Each step's settings are in its guide (*Settings*) and its [control panel](terminology.md#8-the-pipeline) (`run.py`). Give one on the command line as `--<setting> <value>`, e.g. `--records_per_batch 5` (`--records-per-batch 5` works too). A value the step can't use stops it before any input is read or [paid call](terminology.md#8-the-pipeline) made, saying so: one check for every step (`check_settings` in `common/common_helpers/step.py`, run by `run_step` with the step's table of rules, `SPECS` in its helpers), each setting having its kind (a whole number, a number, a text, true or false), its lowest and highest value, or its list of values; a true/false value never passes as a number, and a value from a list is read without case or surrounding spaces (`--part Both` is `both`). One message shape: *The setting <name> must be <what it allows>, but is <value>, so the step can't run. Give --<name> <the nearest bound, or one of the values>, then run the step again.* The table below gives the shared settings' rules; each step's guide its own.

| Setting | Steps | Values |
|---|---|---|
| any true/false setting (e.g. `confirm_paid_calls`) | every step that has one | `true`, `yes`, `on`, or `1`; `false`, `no`, `off`, or `0`; in any case. Anything else stops the step (*expected true or false*). |
| `ids` | 050, 060 | Exactly these records. Either the ids themselves, separated by commas or spaces (`--ids "a1,b2"`), or the path of a file: a value ending in `.txt` or `.csv`, or holding a `/` or `\`, is read as a path. In the file, one id per line: only the text before a line's first comma counts (so a CSV whose first column is the id works), quotes around it removed; blank lines, lines starting with `#`, and a line `id` (in any case) are skipped. An id listed twice counts once. A file that isn't there stops the step (*The setting ids names the file …, which doesn't exist*). |
| `service` | 040, 050, 060, 070 | `litellm` (NASA's LiteLLM, https://proxy.fast.luna.nasa.gov, the default) or `asksage` (NASA's Ask Sage). Each has its own key in `.env` (section 3) and its own model names. Anything else stops the step (*The setting service must be one of asksage, litellm, but is …*). Every cached answer is tied to its service and model. |
| `model` | 040, 050, 060, 070 | A model's name, as the service names it: `py helpers/models.py --service <service>` lists the models the service shows your account; a listed one may still refuse you, which the run's [test call](terminology.md#8-the-pipeline) finds out for the price of that call. Empty stops the step (*The setting model must be a text (not empty), but is …*). Every cached answer is tied to its model (and service): another model asks everything again, and switching back reuses the earlier answers. Which model where: *Choosing a model* (section 5). |
| `thinking` | 040, 050, 060, 070 | `low` (the default; 050's default is `medium` since 2026-10-30), `medium`, `high`, or `model_default` (nothing sent). Sent only to the models that take it (Gemini 2.5 and later, through LiteLLM); their thinking counts against the longest answer allowed (*The thinking cap*, section 5). Anything else stops the step (*The setting thinking must be one of low, medium, high, model_default, but is …*). |
| `repeat` | 040, 050, 060, 070 | A whole number from 1 on: which repeat of this recipe the run is. `1` (the default) reuses the answers saved so far; `2`, `3`, ... are asked again, each into cached answers of its own, so repeats of one recipe are independent answers of the model, and their spread is the model's own variation (*Repeats: how much the numbers vary on their own*, section 5). Not sent to the model. Anything else stops the step (*The setting repeat must be a whole number from 1 on, but is …*). |
| `workers`, `max_chars` | 040, 050, 060 | `workers`: a whole number from 1 to 64, how many [model calls](terminology.md#8-the-pipeline) are made at the same time. `max_chars`: a whole number from 1,000 to 1,000,000, the longest text sent in one call (050's and 060's must be equal). Anything else stops the step (*The setting workers must be a whole number from 1 to 64, but is …*). |

## 5. The steps that cost money: 040, 050, 060, 070

Each sends [texts](terminology.md#1-records-and-their-text) to the AI [model](terminology.md#8-the-pipeline), and each request is a [paid call](terminology.md#8-the-pipeline). Before its first call, each one prints its plan (how many calls, which model) and waits: **Enter** goes ahead, and so do `y` and `yes` (in any case, spaces around them ignored); anything else, or no keyboard attached (a run whose input is closed), stops it (`stopped`), and Ctrl+C interrupts it (`interrupted`), having spent nothing. Every question a step asks before paying takes these answers (070's question about its warnings, and `py helpers/models.py --try`'s, too). If the [run](terminology.md#8-the-pipeline) can't do exactly what you asked, it says so above that question. Its first call is the [test call](terminology.md#8-the-pipeline), a one-line check that your key and the model work, so a mistake costs one call, not hundreds.

Every model answer is kept in the [step](terminology.md#8-the-pipeline)'s `cache/` folder under `outputs/`, so a rerun pays only for what isn't there yet. **Don't delete `outputs/`** unless you mean to pay for those calls again.

**What a saved answer depends on.** Each answer in a step's `cache/` is filed under a fingerprint of exactly these four, and nothing else: (1) the model, as the cache names it: through Ask Sage, the model's name alone (as before a second service existed, so the answers paid for then stay valid); through LiteLLM, the service and the model (`litellm:<model>`), since two services may give one name to different models; (2) the thinking cap, only when one is sent (*The thinking cap*, below); (3) the repeat, only from 2 on (the setting `repeat`), so each repeat has answers of its own and repeat 1 keeps the answers saved before; (4) the prompt exactly as sent: the step's prompt file with everything filled into it (the rules and the reply format of `common/common_prompts/`, the schema, the [text piece](terminology.md#1-records-and-their-text), the batch of [component instances](terminology.md#2-triples), …). Change any of them and that answer is asked, and paid for, again; every other answer is reused. So editing a prompt file asks again exactly the calls that use it: the files of `common/common_prompts/` are used by 040, 050, and 060 alike, so editing one asks all three again. Not part of it: the temperature (changing it in `common/common_helpers/llm.py` reuses the old answers), the code that reads the answers, and `MAX_ANSWER_TOKENS`, which counts only for an answer cut off at it (*A cut-off isn't paid for twice*, below). A cache file that can't be read (cut short, or edited by hand) is treated as empty, so its answers are asked again: it is first copied aside as `<stage>.unreadable.json` (then `-2`, `-3`, …), and the run warns, naming both files (code: `common/common_helpers/cache.py`). Two runs writing one cache file at once (two repeats in two terminals) each merge what the other wrote, under a lock file beside it, so no paid answer is lost.

### While a step pays: what you see, and the guards

After you press Enter, the step prints:

- **The [test call](terminology.md#8-the-pipeline)'s result**, in one line, e.g. `test call: ok (answer 3 tokens, thinking 120 tokens)`. Tokens are the units the service counts and bills; *thinking* is explained under *The thinking cap* below.
- **Progress**, e.g. `model calls: 3 of 12 done, 0 failed, about 1 min left`: at most one line every 10 seconds, and always for a [stage](terminology.md#8-the-pipeline)'s first and last call, so 2 calls show 2 lines and 36,000 calls don't flood the screen. Until 3 calls have finished it says *estimating the time left…*. The stages that ask one prompt at a time (040's labeling, merging, and defining; 070's translations) show `model calls: N done, 0 failed`. Cut-offs are counted among the failed ones, e.g. `1 failed (1 cut off)`.

The [report](terminology.md#8-the-pipeline)'s *Model calls* section then gives the totals: calls, tokens sent and received, thinking tokens (where the service reports them), failed calls, and cut-offs.

**The thinking cap (the setting `thinking`).** Some models think before they answer: they write reasoning you don't see, billed as answer tokens, and it counts against the longest answer allowed (`MAX_ANSWER_TOKENS` in `common/common_helpers/llm.py`, 32,000 tokens since 2026-10-30, 16,000 before; Google's [Gemini thinking docs](https://ai.google.dev/gemini-api/docs/thinking) say the limit includes the thinking, and Anthropic says to "leave room in `max_tokens` for the thinking" ([What's new in Claude Opus 5.5](https://platform.claude.com/docs/en/models/opus-5-5/whats-new-opus-5-5))). Thinking that isn't capped can use most of those tokens and leave the answer cut off: on 2026-10-21, `gemini-2.5-pro`'s answer for a 1,503-character [record](terminology.md#1-records-and-their-text) was cut off after 10,623 characters. Each step that pays has the setting `thinking` (its values: section 4, *Settings several steps share*); `model_default` sends nothing, so the model thinks as it does by default. It is sent as LiteLLM's `reasoning_effort`, and only where LiteLLM documents it ([LiteLLM's Gemini page](https://docs.litellm.ai/docs/providers/gemini)): to Gemini 2.5 and later. For Gemini 2.5 Pro, whose thinking can't be turned off, LiteLLM makes `low` a thinking budget of 1,024 tokens, so the answer keeps about 31,000 of the 32,000; for Gemini 3, the thinking level `low`. Nothing is sent to Claude models: on Claude Opus 5.5 adaptive thinking is always on, and the model decides whether and how much to think, at the effort it is sent or, when none is sent, at its default, `medium` ([Anthropic's effort docs](https://platform.claude.com/docs/en/build-with-claude/effort)), and whether LiteLLM passes an effort on to it isn't shown yet (*Checking that LiteLLM passes Claude's effort on*, below), so the pipeline sends none, and each run's record says `effort: not sent (model default, medium)`; nothing is sent to other models (they might refuse a parameter they don't take), nor through Ask Sage. When the cap is sent, it is part of each cached answer's [fingerprint](terminology.md#8-the-pipeline): changing it asks those calls again. Whether more thinking gives better answers here isn't measured yet; to find out, compare runs (`py helpers/compare_runs.py`).

**The test call's check.** If the test call's one-line answer is cut off, the step stops: every answer would be. If its thinking used half or more of the 32,000 tokens, the step warns, says which setting to change, and asks again before paying for more (with `confirm_paid_calls` false it goes on, and the warning is in the report).

**The early stop.** When 3 of a [run](terminology.md#8-the-pipeline)'s first 10 [model calls](terminology.md#8-the-pipeline) about records' [text pieces](terminology.md#1-records-and-their-text) (040's extraction, 050's drafting, 060's extraction) fail (cut-offs included; `EARLY_STOP_FAILURES` and `EARLY_STOP_WINDOW` in `common/common_helpers/llm.py`), the step stops before paying for more, naming the records, why each failed, and what to change. The calls already under way are waited for, and their answers kept in the cache; the rest aren't made. Failures after the first 10 calls don't stop the run: the records they belong to are left out and listed in the report's warnings. The stages that ask one prompt at a time (040's labeling, merging, and defining; 070's translations) make few calls, and 040's labeling expects some failures (it asks a refused batch again in halves to find the item refused), so the early stop doesn't watch them.

**A cut-off isn't paid for twice.** An answer cut off is kept in the cache as cut off: a rerun with the same settings reports the failure again without a call, since asking again would get the same cut. Through LiteLLM, a cut-off is the service's finish reason `length` (the answer reached `MAX_ANSWER_TOKENS`); through Ask Sage, which takes no answer limit and reports no finish reason, it is an answer that stops inside an unfinished JSON object (the model's own limit cut it). One rule judges every reply, whichever service sent it (`classify_reply` in `common/common_helpers/llm.py`): complete, cut off, refused, empty, or malformed, from the finish reason and the answer's content together. Raising `MAX_ANSWER_TOKENS`, or changing `thinking` for a model it is sent to, asks again; through Ask Sage, where there is no limit to raise, a lower `max_chars` or another model does. A refusal (the service's content filter, or the model declining in prose, even as HTTP 200 with finish reason `stop`) is recognized as a refusal, recorded as one (the failed-call record, the report's *Records left out*), never asked once more in the run and never stored as an answer; the next run asks it again, like any other failure.

**The failed-call record**, `outputs/logs/<run id>_failed_calls.jsonl`, beside the run's [log](terminology.md#8-the-pipeline): one line for each model call that failed, was cut off, or wasn't made because of the early stop (`outcome`: exactly one of `failed` (a failure other than a cut-off), `cut_off`, or `not_sent`; the counter `OUTCOMES` in `common/common_helpers/llm.py` counts each cut-off both under `cut_off` and inside `failed`, so the file has `failed` + `not_sent` lines), with when, the step and run, the stage (`stage`: `test call`; 040's `extract`, `label`, `merge`, `define`; 050's `draft`; 060's `extract`; 070's `map_component_classes`, `suggest_component_classes`) and, for a call about a record's text, the record and text piece (`record`, `text_piece`, counted from 1), the model and every setting the call was sent with (`thinking` among them, and each setting as the request sent it), the prompt's fingerprint and size and the request's size, the service's finish reason (and the model maker's own, when the service passes it on), its token counts (prompt, answer, thinking) and its whole usage, the HTTP status and the service's error message, the error and its type, how many attempts were made and how long they took, the answer received (a cut-off one whole), and what to change. It is written only when something fails; the report's *Run* table and the run's last lines name it. It never holds a key. It's in `outputs/`, so it isn't in Git: to get help with a failure, share this file.

The cheapest way to check that everything works, about 20 [paid calls](terminology.md#8-the-pipeline) in all:

2. **040–070: tiny runs**, in order:

   | 050 | `py 050_annotate/run.py --records_per_batch 1` | 2 (one [record](terminology.md#1-records-and-their-text), and the [test call](terminology.md#8-the-pipeline)) |
   | 060 | `py 060_extract/run.py` | 3 (the finished [ground truth](terminology.md#4-ground-truth-and-samples) records, 2 as of 2026-10-01, and the test call) |
   | 070 | `py 070_evaluate/run.py` | 2 the first time ([component class](terminology.md#3-schemas) translations, and the test call); it then stops so you can check the rows it added to `annotations/component_class_mapping.csv`. Run it again: 0 calls, or 2 (the test call, and the suggestion call: a row says `(none)` while the [ground truth schema](terminology.md#3-schemas) has a component class of the same kind that nothing translates to). |

3. **Check you're charged properly.** For each [run](terminology.md#8-the-pipeline), compare the plan it prints before you press Enter ("… will make N [model call](terminology.md#8-the-pipeline)(s) …") with its [report](terminology.md#8-the-pipeline)'s *Model calls* table (`outputs/reports/<run id>.md`): calls per [stage](terminology.md#8-the-pipeline), the test call, and the total paid. Running the same command again should show 0 paid calls: the cache works, and nothing is paid twice.

Nothing is wasted: the real 040 run reuses the tiny run's saved answers; 050's record is real work (correct it in `py helpers/annotate.py`); 060 and 070 simply run again after the real 040.

### Repeats: how much the numbers vary on their own

One run isn't a baseline: the same recipe can give somewhat different numbers on another run, because the model doesn't answer the same way every time, and a rerun normally reuses the saved answers, so it can't show that. The setting `repeat` asks again: each repeat of a recipe gets answers of its own. To measure the noise floor of extraction (060) on the finished [tuning records](terminology.md#7-evaluating-extraction-step-070), run, in this order (070 reads 060's latest output, so evaluate each repeat before the next):

```
py 060_extract/run.py --repeat 1
py 070_evaluate/run.py
py 060_extract/run.py --repeat 2
py 070_evaluate/run.py
py 060_extract/run.py --repeat 3
py 070_evaluate/run.py
py helpers/compare_runs.py <070 run id of repeat 1> <070 run id of repeat 2> <070 run id of repeat 3>
```

Each 060 repeat pays for all its calls (repeat 1 reuses what is already saved for this recipe); keep 070's own `repeat` at 1, so the three evaluations use the same translation proposals. Step 070 stops while a row of the [translation table](terminology.md#7-evaluating-extraction-step-070) is unchecked: check the rows first (`py helpers/annotate.py`). Note each 070 [run id](terminology.md#8-the-pipeline) (top of its report). `compare_runs` then shows, under *Spread across the runs*, each number's lowest, highest and mean value and the width between them: the model's own variation on these records. Whether a later change helped is decided by the rule fixed before the runs, not by that width: run the change's repeats the same way, then `py helpers/compare_runs.py --baseline <070 run ids of the baseline's repeats> --changed <070 run ids of the change's repeats>`; partial F1 alone decides, and the verdict is *helped*, *worse* or *can't tell apart* (`helpers/compare_runs.md`, *Did a change help?*).

### Choosing a model

Each of 040–070 has a `service` [setting](terminology.md#8-the-pipeline), the service that reaches the model (its values: section 4, *Settings several steps share*). Each service names its [models](terminology.md#8-the-pipeline) its own way (Ask Sage's `google-claude-sonnet-5` is LiteLLM's `claude-sonnet-5`), and each step has a `model` setting: by default `claude-opus-5-5` for 040, 060, and 070, and `gemini-2.5-pro` for 050 (LiteLLM names, as `py helpers/models.py` lists them; until 2026-11-01 the first was spelled `claude-opus-5.5`, which LiteLLM accepts without listing: `docs/findings.md`, 2026-11-01). On 2026-10-12, LiteLLM let this project's key use both, and `gemini-3.1-pro-preview`; Ask Sage refused Opus. LiteLLM's `gpt-5.5` refused the pipeline's temperature 0 (it accepts only 1), so GPT-5 models can't be used as the code stands. Temperature 0 is sent only to the models that take it (`temperature_sent` in `common/common_helpers/llm.py`): not to Claude models, which take no sampling parameters ("Omit `temperature`, `top_p`, and `top_k`": [Claude Opus 5.5 migration guide](https://platform.claude.com/docs/en/models/opus-5-5/migration-guide)), and not to Gemini 3 and later, whose maker advises keeping its default ([Gemini 3 guide](https://ai.google.dev/gemini-api/docs/gemini-3)); each run's record says what was sent. To see which models a service lists for your account (free; LiteLLM's list shows only the models your key may use; add `--service asksage` for Ask Sage's):

```powershell
py helpers/models.py
```

A listed model may still refuse you: Ask Sage's list shows what it offers, not what your account is approved for, and a model LiteLLM lists may still fail on a setting it doesn't accept. To find out, try the models you're considering, e.g. `py helpers/models.py --try claude-sonnet-5 <name> <name>`, with names copied from the list, or `--try all` for every listed one. Each try is the one-line [test call](terminology.md#8-the-pipeline) a [step](terminology.md#8-the-pipeline) makes first: one tiny [paid call](terminology.md#8-the-pipeline) per model, asked about before paying. It prints each model as usable, or refused with the service's reason (e.g. Ask Sage's `model_not_permitted`).

**Checking that LiteLLM passes Claude's effort on.** On Claude Opus 5.5 adaptive thinking is always on: the model decides whether and how much to think, and the effort setting is the main control of how much ([Anthropic's effort docs](https://platform.claude.com/docs/en/build-with-claude/effort)). Before the pipeline sets an effort itself, find out whether LiteLLM forwards one. The check has two steps, and each asks before it sends anything:

```powershell
py helpers/check_effort.py
```

- **Step A, an invalid value** (two requests, expected to cost nothing). It sends `reasoning_effort` "not_a_level", then `output_config` effort "not_a_level". A refusal naming the setting (HTTP 400 or 422 whose error text names `reasoning_effort` or `output_config`) means the setting is read on the way, by LiteLLM's check or Anthropic's; the error text it prints says whose. An answer (HTTP 200) means the setting was dropped or ignored. Any other reply gives no verdict and says what it is about instead: a 400 or 422 not naming the setting (something else in the request), a 401 (the key), 403 (your access), 404 (the model name), 429 (the rate limit), or a server error. A refused request produces no answer and reports no tokens; a request that is answered instead is a tiny paid call.
- **Step B, a question that needs reasoning** (nine paid calls). It asks a counting puzzle whose answer, 168, is checked, 3 times each with no effort, at `low` and at `high`, and prints each call's completion tokens, the mean per setting, and whether each answer is right. Before the calls it prints its decision rule: "passed on" if every high call uses more completion tokens than every low call, or the mean of high is at least 1.5 times the mean of low; "not shown" otherwise, and also when a call failed. Completion tokens are the measure because Anthropic counts thinking inside the billed output tokens, so they include the thinking even when the service reports 0 reasoning tokens.

`py helpers/check_effort.py --only a` or `--only b` runs one step. Put what it prints in `docs/findings.md`.

**Checking LiteLLM's answer cache.** LiteLLM's proxy can keep answers and give a repeated identical request the kept answer ([LiteLLM caching](https://docs.litellm.ai/docs/proxy/caching)). If NASA's does, the runs of a recipe's repeats (*Repeats: how much the numbers vary on their own*, above) get the same answers, not new ones. On 2026-10-31, `check_effort.py` got exactly the same completion-token count for the 3 identical requests of each setting (717, 814 and 802), which suggests it does. To find out:

```powershell
py helpers/check_answer_cache.py
```

It asks the model for one sentence about the Moon 4 times (4 tiny paid calls, asked about before sending): twice as it is, then twice with LiteLLM's per-request cache control `{"cache": {"no-cache": true, "no-store": true}}` ("Force a fresh response, bypassing the cache", and don't keep it: [LiteLLM cache controls](https://docs.litellm.ai/docs/proxy/caching_controls)). For each call it prints the HTTP status, whether the reply carries the header `x-litellm-cache-key` (LiteLLM puts it on an answer from its cache), the completion tokens, the answer, and every cache-related field. Before the calls it prints its decision rule: "LiteLLM answers from its cache" if the second plain call carries `x-litellm-cache-key` or returns a byte-identical answer with identical usage, while the no-cache calls differ from each other or carry no `x-litellm-cache-key`; "no answer cache seen" if no call carries the header and the two plain answers differ; "not shown" otherwise, with the reason. It also says whether the proxy accepted the cache control (no HTTP 4xx) and what to do. If LiteLLM answers from its cache and the control is accepted, put the line `LITELLM_BYPASS_ANSWER_CACHE=1` in `.env`: every LiteLLM request of 040, 050, 060 and 070 (and of the checks) then carries the control, and the step's own `cache/` is the only reuse; the words the model gets, the cache keys and the prompts' fingerprints don't change. Each run's record (`answer_cache`) and report (*Model calls*) say "LiteLLM answer cache: bypassed" or "not bypassed". The control is off until then because LiteLLM's docs don't say whether a proxy with its cache off accepts it. Put what the check prints in `docs/findings.md`. Run on 2026-11-01: LiteLLM answers from its cache, the control is accepted, and the NASA laptop's `.env` has the line since that day (`docs/findings.md`).

Which model where:

- **040, 050, 070: the strongest model that answers you.** Their calls are few (tens to a few hundred), and their quality matters most: 040 shapes the induced [schema](terminology.md#3-schemas), 050 decides how much you correct by hand, 070's translations decide the metrics.
- **050 and 060: two different models, from different makers if you can** (e.g. a Claude model for one, a Gemini or GPT model for the other). The [ground truth](terminology.md#4-ground-truth-and-samples) starts as 050's [drafted triples](terminology.md#4-ground-truth-and-samples); if 060 used the same model, the [facts](terminology.md#2-triples) that model misses would be missing from both, and [recall](terminology.md#7-evaluating-extraction-step-070) would look better than it is. Step 060 warns before paying when it would extract with the model that drafted the ground truth, or one from the same maker. The same holds for every pair of steps whose models check each other (040's schema, 070's proposed rows of the [translation table](terminology.md#7-evaluating-extraction-step-070), the [second opinion](terminology.md#4-ground-truth-and-samples)): the full list, what each can inflate, and what 070 reports for it, is [shared-model bias](terminology.md#7-evaluating-extraction-step-070) (`070_evaluate/070_evaluate.md`, [*Shared-model bias*](../070_evaluate/070_evaluate.md#shared-model-bias)).
- **060 on every [record](terminology.md#1-records-and-their-text) (about 36,000 calls): measure before choosing.** Once 20 or more [tuning records](terminology.md#7-evaluating-extraction-step-070) are finished, run 060 on them with two or three models, evaluate each with 070, compare them (`py helpers/compare_runs.py`, `helpers/compare_runs.md`), and use the cheapest that the comparison can't tell apart from the best.
- **Decide before the real runs:** every cached answer is tied to its model, so changing models later means paying for those calls again.

### A second opinion on the ground truth (added 2026-11-01)

Many ground truth triples were first drafted by a model and corrected by hand, and the rest written by hand, so the facts the drafting model missed were found by one person alone. To know which ground truth triples a second, independent annotator also finds, another model drafts every [finished record](terminology.md#4-ground-truth-and-samples) again, the way 050 drafts, in 3 repeats (each with answers of its own), and each [ground truth triple](terminology.md#4-ground-truth-and-samples) is matched against those fresh drafts (`helpers/second_opinion.md`). The [ground truth](terminology.md#4-ground-truth-and-samples) isn't changed. Once some records are finished:

```powershell
py helpers/second_opinion.py
```

It asks once before paying for all 3 repeats (the plan shows 3 repeats × the [text pieces](terminology.md#1-records-and-their-text), and how many are already in the cache; its notes say which records it drafts, by part; `--repeats <n>` for another number of repeats; `--ids <id>,<id>` for some of the records; `--model <name>` for another model than `gemini-4-argon`). Keep `LITELLM_BYPASS_ANSWER_CACHE=1` in `.env`, so LiteLLM doesn't answer the repeats from its own cache. Read its report: the counts found in at least one repeat / found in none, how many repeats found each ground truth triple, and, for [tuning records](terminology.md#7-evaluating-extraction-step-070) only, the draft's facts the ground truth lacks, to review (a missed fact, one the rules leave out on purpose, or a wrong one). Then record what was found, so step 070 reports recall by the group found in at least one repeat / found in none, and the draft's facts the ground truth lacks, to review, and bring both files to the personal laptop through Git:

```powershell
git pull
py helpers/second_opinion.py --apply true
git add annotations/second_opinion.csv annotations/second_opinion_candidates.csv
git commit -m "Second opinion applied"
git push
```

`git pull` first, so that a decision already filled in `annotations/second_opinion_candidates.csv` is kept. Applying pays nothing (the 3 repeats' answers are cached) and writes `annotations/second_opinion.csv` and `annotations/second_opinion_candidates.csv`, the only files of `annotations/` it ever writes: the second one lists, for the tuning records only, the draft's facts the ground truth lacks, each with an empty column `decision` that I fill when I review it against the record and the rules (`helpers/second_opinion.md`, *The draft's facts to review*); a rerun keeps every decision already filled. A wrong `decision` stops the run before it pays, naming the line. Apply again after rewording or adding ground truth triples of a finished record (a reworded one counts as not checked until then; step 070 warns).

### Comparing with the ground truth schema (added 2026-11-01)

To see how far the [induced schema](terminology.md#5-learning-the-schema-step-040)'s numbers are from those of the schema the [ground truth](terminology.md#4-ground-truth-and-samples) uses, 060 extracts once with the [ground truth schema](terminology.md#3-schemas) itself. Step 070 recognizes such a run and translates every [component class](terminology.md#3-schemas) to itself, in memory: it doesn't read the [translation table](terminology.md#7-evaluating-extraction-step-070), adds no row, asks the model nothing, and so can't change the rows the baseline's repeats use (`070_evaluate/070_evaluate.md`, *Comparing with the ground truth schema*). Run it after the baseline's repeats (*Repeats: how much the numbers vary on their own*, above), never between a repeat's 060 and its 070, since 070 reads 060's latest output:

```powershell
py 060_extract/run.py --schema annotations/ground_truth_schema.txt
py 070_evaluate/run.py
py helpers/compare_runs.py --across_schemas true <070 run id of repeat 1> <070 run id of the run above>
py 060_extract/run.py --repeat 1
```

The first command pays for every [text piece](terminology.md#1-records-and-their-text) once (the ground truth schema makes other prompts); the second pays nothing. Its report says, under *What this run worked on*, "Translation: identity (060 used the ground truth schema)", and so does its recipe. The third compares it with repeat 1: without `--across_schemas true` it refuses to put a run by identity beside one through the translation table; with it, the report is titled *Comparing evaluations across schemas* and says that each difference measures the schema and its translation together, not extraction alone. The fourth puts 060's output back to the induced schema's repeat 1 (its answers are saved: nothing paid), so a later `py 070_evaluate/run.py` evaluates the baseline again. The ground truth schema was shaped while annotating the very [tuning records](terminology.md#7-evaluating-extraction-step-070) evaluated, so read its numbers as a reference for the induced schema's, not as a held-out result. If 070 stops with *Step 060's last run extracted with the ground truth schema, but … no longer matches*, the ground truth schema changed after 060 ran: run the first command again (paid), then the second.
