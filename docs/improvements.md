# Improvements list

The changes to make to the pipeline itself: what to change, why, and where the idea came from. Not to be confused with the upkeep (`upkeep.md`): what a person running the pipeline does, and when. An item that is done is deleted here, and the commit that does it says so. Measured results that an item rests on are in [`findings.md`](findings.md).

## The whole pipeline

- **Repeat runs, to measure run-to-run noise.** A setting that skips the saved answers, so that a step can be run again with exactly the same settings. One run isn't a baseline: two runs of step 040 with the same settings, differing only by one rule of the prompt (rule 8), spelled 41 of the 63 entity classes and 67 of the 126 predicates the same. From: [`findings.md`](findings.md), 2026-10-12.
- **Cost per run.** Each report already gives the tokens sent and received (section *Model calls*); a price per token would turn them into dollars. From: the literature review of 2026-10-07.
- **A batch API at NASA's LiteLLM**, if it has one: many calls sent together, at a discount. Ask NASA's LiteLLM administrators. From: 2026-10-13.
- **Keep the saved answers safe:** every model answer behind a reported number is in the steps' `cache/` folders under `outputs/`, which Git doesn't carry, so they exist only on the computer that ran the step. Archive them with each run that numbers are reported from. From: the methods review of 2026-10-11, item 7.
- **`tests/run_all.py` on the NASA laptop:** its first run there reported that the tests changed files, and the next run passed. Find why. From: 2026-10-12.
- **README, *How to reproduce*:** setup and running are in [`running_on_nasa_laptop.md`](running_on_nasa_laptop.md); building the graph waits for step 080. From: my old to-do list.
- **Other catalogs:** some things fit only data.nasa.gov. The catalog's address is fixed in the code (`010_harvest/010_harvest_helpers/ckan_client.py`); "undefined" is treated as a maintainer (`020_clean/020_clean_helpers/maintainers.py`); splitting into strata needs a maintainer field that other catalogs may not fill; step 040's prompts say "a catalog of NASA datasets". From: the methods review of 2026-10-11, item 11.
- **Competency questions:** 10 to 20 questions the knowledge graph should answer, to judge it by. From: the literature review of 2026-10-07.
- **An entity class hierarchy for the schemas:** the ground truth schema is flat (no entity class is a kind of another). An umbrella entity class with subclasses is standard in knowledge graph schemas (subClassOf in RDF Schema); for people and groups it has a standard name, Agent, with Person, Organization and Group under it (FOAF; PROV-O). With it, a pin could say any -> Agent instead of listing Organization, Person and Team (DEVELOPED_BY_PARTY, SPONSORED_BY_PARTY), and the graph could answer questions across the kinds. It touches the schema reader and its file format, the pin check, step 040's induced schema, and step 070's translation table, so it is a design change for after the first run. Some entity classes only ever appear as the object of one predicate, and their definitions just restate it: Purpose (HAS_PURPOSE), Task (RESPONSIBLE_FOR), Role (SERVES_AS), ProcessingLevel (HAS_PROCESSING_LEVEL), SpatialRepresentation (HAS_SPATIAL_REPRESENTATION). They cause no disagreement today, unlike Value and Time, which were merged for that reason on 2026-10-20; with a hierarchy they could sit under one umbrella entity class (e.g. Label). From: 2026-10-20.

## 040_induce_schema

- **The sample of texts:** 10 maintainers × 15 texts is the documented baseline, not a design shown to be best. Taking only the 10 largest maintainers, it can never sample the records of the others (about 8% of the catalog, on the 2026-09-27 harvest; the methods review of 2026-10-11, item 3). Compare designs with `helpers/compare_runs.py`, guided by the saturation curve in 040's report. From: [`findings.md`](findings.md), 2026-10-12.
- **`min_support`** above 1 (it is 1, which keeps everything found): try other values once runs can be compared. From: 040's guide, *Settings*.
- **Near-duplicate texts inflate support.** If a maintainer's 15 texts are nearly the same text, every schema entry found in them counts 15 times. Measure how alike each maintainer's texts are; then drop the near-duplicates (taking others from the same maintainer), or count that maintainer once. It matters once `min_support` is above 1. 040's report lists twins between the texts it learned from and the pool, not near-duplicates among its own texts. From: my old to-do list.
- **Nothing filters junk from stage 2:** e.g. "dataset" as a bare subject instance, or "VNP43D66 is the BSA" read as an "is a" statement, both gaining real support. A list of generic subject instances to drop would cost nothing. From: my old to-do list.
- **Alternatives to stage 4 (merging synonymous labels):** grouping by similarity, passing the chosen labels forward from batch to batch, or another approach entirely. From: my old to-do list.
- **Which text fields to learn from:** 040 uses `title` and `notes` and any field 020's `extra_text_fields` adds; which other fields help is untested. First candidate: the names of the files attached to a record (e.g. `…L3m.8D.SST4…nc`), which can say what a dataset holds when its notes describe several (2026-10-19, record #4). From: my old to-do list.
- **Ideas to compare the induced schema with:** the Purview glossary, Neo4j's capabilities, the five science domains of NASA's Science Mission Directorate (SMD) site, and the filters data.nasa.gov's search offers. From: my old to-do list.

## 050_annotate

- **Clean up the definitions and rules written while annotating batch 0:** the ground truth schema's entries coined or redefined then (SpatialExtent, SpatialRepresentation, Value, TimeOfDay, Algorithm, Identifier, and the rest), and the annotation guidelines' rules added or changed then (rules 6, 9, 10, 11, 12, 13, and 14 of *Writing a classed triple*), in their wording; then check that the model's copy of the rules (`common/common_prompts/extraction_rules.txt`), which the drafting (050) and extracting (060) prompts include, says the same. From: 2026-10-18.
- **A near-duplicate check when coining:** before the annotation tool adds a coined entity class or predicate, show the closest ones already in the ground truth schema, by spelling (`Satelite`, `Satellite`) and by words shared with their spellings and definitions, with a button to use one instead. A model would also catch synonyms that share no words (`Probe`, `Spacecraft`), at a paid call each. For now, coined ones are reviewed together at the end of a drafted batch. From: 2026-10-14.
- **Less work per annotated record:** measure the time per record on batch 0 first; then decide what to automate (e.g. a second model checking each drafted batch and pointing at doubtful component classes, so a person looks only there). From: 2026-10-06 (queued), 2026-10-14.
- **Gemini 2.5 Pro and error 500:** in a test with an answer limit of 20 tokens it answered error 500 ("no choices"), probably its thinking using up the limit. Watch whether real drafting calls get it: each costs retries. From: [`findings.md`](findings.md), 2026-10-12.
- **A drafted record cut off at the answer length limit:** on 2026-10-21 I ran `py 050_annotate/run.py --records_per_batch 2` on the NASA laptop (default model `gemini-2.5-pro`, through LiteLLM). Record d5477563-0415-4e65-ab7c-d4bc9ed809e5 (pool position 7, MODIS/Terra Land Surface Temperature/Emissivity Daily L3 Global 1km SIN Grid V006) failed: "piece 1: the answer was cut off at the longest length allowed (16,000 tokens, MAX_ANSWER_TOKENS in common/common_helpers/llm.py), after 10,623 characters"; the other record (pool position 6) drafted 15 triples. Verified: the record's text is 1,503 characters, one text piece (050's `max_chars` is 8,000), and 050 sends `max_tokens` = `MAX_ANSWER_TOKENS` with no setting for the model's thinking. Suspected: 10,623 characters of answer are far fewer than 16,000 tokens hold (about 3 to 4 characters a token is usual), so most of the tokens went somewhere I can't see; the likely place is Gemini 2.5 Pro's thinking, which it does before answering and which counts against the limit (the error 500 entry above is the same suspicion). Also suspected: 10,623 characters is long for a 1,503-character text, so the visible answer may repeat itself. The step's log on the laptop (`outputs/logs/<run id>.log`, the DEBUG line starting "cut-off answer") has the whole answer and the service's token counts (the reasoning tokens, if LiteLLM reports them), which would settle both. Running it again unchanged would get the same cut (temperature 0). Lowering `max_chars` wouldn't help: the text is already one short piece. Candidate fixes: cap the thinking for models that think (e.g. LiteLLM's `reasoning_effort`, or a thinking budget); raise `MAX_ANSWER_TOKENS` for such models (Gemini 2.5 Pro allows longer answers); if the answer repeats itself, look at the prompt instead. From: 2026-10-21. **Done on 2026-10-22:** the thinking cap, the setting `thinking` of every step that pays (default `low`: for Gemini 2.5 Pro, LiteLLM's 1,024-token thinking budget; sent only to Gemini 2.5 and later); the test call's thinking tokens shown, with a warning when they leave little room; the early stop (3 failed among a run's first 10 calls); a cut-off answer not paid for twice; thinking tokens and cut-offs in the report; and the failed-call record (`outputs/logs/<run id>_failed_calls.jsonl`), which keeps a cut-off answer whole with its token counts (all in `docs/running_on_nasa_laptop.md`, section 5). From now on, every failed call also lands in the failed-call record with its prompt, answer, and thinking tokens and its finish reason. **Root cause confirmed on 2026-10-22:** Gemini 2.5 Pro's hidden thinking took 12,615 of the 15,996 answer tokens (79%), leaving 3,381 for the visible answer (numbers in [docs/findings.md](findings.md#2026-10-21--step-050--why-a-drafted-answer-was-cut-off)); the thinking cap above addresses it. **Still open:** draft record d5477563-0415-4e65-ab7c-d4bc9ed809e5 again with the default `--thinking low`, to check it now fits. **Also open, the thinking cap's trade-off:** less thinking may make the answers worse, and I haven't measured it. To test it: run the same records with `--thinking low`, `medium`, and `high` (or `model_default` with a higher `MAX_ANSWER_TOKENS`) and compare 070's scores; each report records the setting used.
- **Mission or spacecraft, when they share a name (open; to settle with more records):** NASA often gives a mission and its spacecraft the same name (Dawn, Rosetta, Aqua), and a record may name it without saying which. In record #5 (pool position 5), the title "DAWN GRAND MAP VESTA FAST NEUTRON RESIDUAL V1.0" names Dawn only as the first word. Planetary (PDS) titles follow NASA's [PDS3 Standards Reference, Chapter 6](https://pds.nasa.gov/datastandards/pds3/standards/sr/Chapter06.pdf), which builds a dataset's name from up to seven components, starting with the instrument host: the platform carrying the instrument, usually a spacecraft. So the first word is a good clue for the Spacecraft entity class, as with record #1's "ROSETTA-ORBITER". Its limits: the instrument host can also be a ground observatory or an observing campaign; the order of the other components isn't reliable (record #5's title puts the instrument before the target); and Earth-science titles follow other conventions. So it is a clue for the annotator's choice of entity class, not a rule. The graph side (keep same-named Mission and Spacecraft nodes apart) is in step 080's item on joining instances. From: 2026-10-22.

## 060_extract

- **Patterns in or out of the prompt:** patterns are 58% of the schema text (about 14,500 tokens in all). Compare runs with and without them. From: [`findings.md`](findings.md), 2026-10-12.
- **Experiment: the source text first in the model's answer.** The reply asks for subject, predicate, object, and their entity classes, then the source text last, so the model states a fact and finds its passage afterwards. Asking for the passage first, then the fact, may give facts that keep closer to the text. A model that thinks before answering (claude-opus-5.5 does) may gain less. From: Negro, Futia, Kůs, and Montagna, *Knowledge Graphs and LLMs in Action* (Manning, 2026), section 14.7.1.
- **An entity class or predicate that does badly:** try renaming it first (a generic entity class or predicate gave unstable results there; a more specific one fixed it). From: Negro, Futia, Kůs, and Montagna, *Knowledge Graphs and LLMs in Action* (Manning, 2026), section 5.3.3.
- **Prompt size and cost:** measure both on the first run. From: 2026-10-12.
- **The content filter:** in step 040 the service refused phrases from GeneLab (space biology) records. Watch whether 060's failed records cluster there. From: [`findings.md`](findings.md), 2026-10-12.
- **A fixed schema for the full run,** chosen and kept in Git, so that the full run doesn't depend on whatever `outputs/` holds. From: 2026-10-12.
- **Extraction stops short on long records:** in the first evaluation (070 run 2026-10-22_1615, 6 tuning records), 33 of the 73 missed ground truth triples were within reach of the current schema. 17 of them are facts about things other than the dataset (an algorithm's purpose, the channels a variable is computed from, an input's DOIs, an instrument's parts) and 10 are dataset facts simply skipped. Record 03a09af3 (pool position 4, MODIS Aqua SST) alone has 15: its model call finished normally (status extracted, no error, 1 text piece) with 11 extracted triples, against 49 ground truth triples, so it was not cut off. To try, one change at a time and measured against this baseline: a prompt instruction to state the facts about every thing the record names, not only the dataset; splitting long records into more text pieces (lower the setting `max_chars`, default 8,000, below the record's text length). From: 2026-10-22.

## 070_evaluate

- **Raise With Mentors: checking a sample of the occurrences left extracted only,** to see how far precision and recall are understated ([`metrics/pairs.md`](../070_evaluate/metrics/pairs.md), *The same fact in different words*). It's an involved process: such an occurrence can be the same fact in different words as a ground truth triple left ground truth only, a repeat of a fact already paired, a fact the ground truth lacks, the result of a wrong translation, or actually wrong, and each means something different. From: 070's guide, *To do*.
- **About 10 records annotated from scratch,** with no drafted triples: measures how far drafted triples steer annotation (recall may be overstated by a model-drafted ground truth: [`metrics/recall.md`](../070_evaluate/metrics/recall.md)). From: the literature review of 2026-10-07.
- **Listing likely pairs that the wording hides:** pairing compares words, not meaning, so the same fact in other words leaves an extracted only occurrence and a ground truth only triple ([`metrics/recall.md`](../070_evaluate/metrics/recall.md#when-a-ground-truth-triple-counts-as-not-found), row 4). Step 070 could list, per record, each extracted only occurrence and ground truth only triple with the same predicate and the same subject instance or the same object instance (once evened out), e.g. "MODIS" ABOARD "Aqua" and "the imaging spectroradiometer" ABOARD "Aqua", for a person to review in the annotation tool as with partial pairs; a pair marked the same fact would then count. This parallels the component class mismatch check, which finds the same subject and object instances under different predicates. From: 2026-10-24.
- **A second annotator** for a sample of records, to measure agreement between people (Hripcsak & Rothschild 2005). From: the literature review of 2026-10-07.
- **A second person checking a sample of the translation table,** frozen before the held-out part is looked at. From: the literature review of 2026-10-07.
- **Gaps in the translation table** (164 rows, commit f92cf0c), found when reviewing it: (1) the current schema (from step 040) has no predicate for FROM_MISSION or FROM_SPACECRAFT (ground truth schema), though they are common facts about a dataset, so those ground truth triples can never pair strictly and lower recall whatever extraction does; check step 040 for why it doesn't induce them. (2) HAS_OBJECTIVE (current schema) translates to HAS_PURPOSE (ground truth schema), pinned any -> Purpose, but no entity class of the current schema translates to Purpose; check it against step 040's patterns, which exist only in the run on the NASA laptop. From: 2026-10-22.
- **Other quality metrics,** e.g. coverage. 070 already reports partial pairs, entity-class accuracy, and the recall upper bound. From: my old to-do list.
- **The model's run-to-run variation** isn't among the reasons the numbers are approximate ([`metrics/approximately.md`](../070_evaluate/metrics/approximately.md)), and margins of error leave it out. Add it once repeat runs measure it (see *The whole pipeline*). From: the methods review of 2026-10-11, item 6.
- **Comparing runs whose schemas differ:** several component classes of a schema may translate to one of the ground truth schema, so a finer schema is forgiven some wrong entity classes ([`metrics/pairs.md`](../070_evaluate/metrics/pairs.md), row 5 of *When a pair isn't the same fact*). `helpers/compare_runs.py` should say so when the runs' schemas differ. From: the methods review of 2026-10-11, item 10.
- **The 10-point threshold** of 070's warning that a stratum's share of the evaluated records differs from its share of the pool: no source for 10. From: the literature review of 2026-10-07.
- **Citations not yet checked:** Cochran (1977) for the 5% rule and the ratio bias, cited from memory in the metric docs. From: the literature review of 2026-10-07.
- **The partial-pair verdicts in the recipe:** `helpers/compare_runs.py` compares two runs of 070 on records with the same ground truth, but a verdict changed between the runs (`annotations/partial_pair_reviews.csv`) also changes the numbers, and neither the recipe nor the ground truth's fingerprint holds the verdicts. Fingerprint each record's verdicts with its ground truth, so such a record is left out and named. From: the project sweep of 2026-10-14.

Decide which the twins should use, and make the guide and the code say the same. From: the project sweep of 2026-10-14.

## 080_build_graph

- **Before designing 080, read the rest of** Negro, Futia, Kůs, and Montagna, *Knowledge Graphs and LLMs in Action* (Manning, 2026): chapter 3 (RDF or a labeled property graph), chapter 4 (combining several sources: phase 1's graph and phase 2's triples), and chapters 13 and 14 (how people ask questions of a finished graph, for the competency questions). Chapters 5 to 8 and part of 14 were read on 2026-10-14 (the items here citing the book). From: 2026-10-14.
- **Three layers:** the records; each extracted triple as extracted (never joined with another), with its record and source text; and the knowledge graph built from those. The knowledge graph can then be rebuilt without asking a model again, and every edge can show the passage it came from. From: Negro, Futia, Kůs, and Montagna, *Knowledge Graphs and LLMs in Action* (Manning, 2026), section 6.1.
- **A layer of facts from the model's own knowledge:** joining names ("MODIS" = "Moderate-resolution Imaging Spectroradiometer (MODIS)"), reading codes ("MID-IR" in a title meaning SST4), and background facts, each marked as the model's, kept apart from the extracted triples (which stay what the record states), and checked by a person on a sample, with its own accuracy. From: 2026-10-19.
- **A record's node: `Dataset` or `CatalogEntry`?** Phase 1's graph makes each record a node labeled `Dataset`, while the describes triple gives the record the entity class `CatalogEntry` and gives `Dataset` (or `WebTool`, …) to what its title names. Decide which the graph uses before building it. From: the terminology sweep of 2026-10-15.
- **Linking subject instances and object instances to reference lists,** so that one thing named several ways ("Aqua", "EOS PM-1") becomes one node. First processing levels, a short fixed list (L0, L1A, L1B, L2, L3, L4: every spelling, such as "Level 3" or "L-3", mapped to one); then NASA's missions ([A to Z of NASA missions](https://www.nasa.gov/a-to-z-of-nasa-missions/)), where a subject or object instance with no match is marked for a person to check, not dropped, since the catalog also names missions of other agencies; GCMD keywords as another list. How: the subject or object instance keeps the record's words and gets an edge to its entry, saying how the match was made; candidates come from the list, never from a model (exact match after evening out, "Long Name (ACRONYM)" split into both forms, then near spellings as candidates only); a model chooses only among two or more candidates, and may answer "none of these"; a small hand-checked set of subject or object instance → entry (or none) measures it. Aliases ("EOS PM-1" for Aqua) must be written for our lists. From: my old to-do list; 2026-10-13; Negro, Futia, Kůs, and Montagna, *Knowledge Graphs and LLMs in Action* (Manning, 2026), chapters 7 and 8 (which choose without a "none" answer and don't measure linking).
- **Which predicates give properties instead of edges,** by the rule of README, *Phase 1*: a processing level, for example, has few values, which people filter by but don't go from node to node through. From: my old to-do list; 2026-10-13.
- **Splitting a number with a unit** ("250 m") into a value and a unit, as graphs store quantities (Wikidata, QUDT, schema.org's QuantitativeValue). From: 2026-10-11.
- **One written form for every value:** every exported value is written in one form, whatever spelling the record used: a number, a space, and the unit, as the SI brochure prescribes (e.g. 500 m, never 500m; 4.63 km; the only exceptions are °, ′ and ″ of a plane angle, written with no space). Matching (070, the annotation tool) already treats both spellings as the same; the graph must not keep both. From: 2026-10-20; BIPM, *The International System of Units (SI)*, 9th edition (2019), section 5.4.3.
- **A fact many records state:** one edge per extracted triple, or one edge listing the records it came from. Either way, keep which records each edge came from. From: 2026-10-06.
- **Joining subject instances and object instances that name the same thing into one node** beyond the lists: similar spelling plus shared neighbors (two spacecraft names spelled alike that carry the same instrument), grouped into connected components, the longest name kept; generic words ("Data", "Product", "Level") never count as similar. Which subject instances and object instances to join across records, and which to keep as one node per record: specific named things join (one MODIS node, one Aqua, one NASA), since they are important and specific. Generic descriptions don't: "L2 pixels" (record #4, pool position 4), "radiance data" and "a series of screens" (pool position 2) each mean that record's own data or method, so one shared "L2 pixels" node would wrongly connect unrelated datasets. Matching words alone can't tell the two kinds apart, so 080 needs a test for it: e.g. a proper name or an acronym against a common noun phrase, or a model's judgment checked on a sample. Organizations inside organizations: the ground truth keeps an organization's name whole, as written (e.g. "NASA Ocean Biology Processing Group (OBPG)", pool position 4), because "NASA" there says whose group it is, while in "NASA Technical Standards Program" (pool position 0) it is part of the name, and wording alone can't tell the two apart. So 080 should add part-of edges (OBPG part of NASA) from a known list of NASA's organizations, not from the words, so that such groups connect to the one NASA node. Groups named with a person: rule 12 of the annotation guidelines keeps "Peter Minnett and his team" (pool position 4) whole as one instance, because "his team" alone isn't complete. So that node won't join a "Peter Minnett" node from another record; 080 should link the two (the team includes the person) rather than leave them unconnected. Same name, different things: NASA often gives a mission and its spacecraft the same name (Dawn, Rosetta, Aqua). A Mission node and a Spacecraft node with the same name must stay two nodes, never joined because the names match. They may be linked (the spacecraft belongs to the mission), but only from a record that states it. From: Negro, Futia, Kůs, and Montagna, *Knowledge Graphs and LLMs in Action* (Manning, 2026), section 6.1.4; 2026-10-19; 2026-10-22.
- **Checks of the graph:** how well nodes were joined (precision and recall of the joining), duplicate nodes, and a person checking a sample of edges. From: the literature review of 2026-10-07.
- **Phase 1's maintainers:** README's table says 434 Maintainer nodes, but 020 joins maintainer spellings down to 422. Rebuild phase 1's part with 020's cleaning. From: my old to-do list.
- **More edges from the metadata fields other than the text fields** (phase 1): fields not used yet may give more edges, or properties. From: my old to-do list.
