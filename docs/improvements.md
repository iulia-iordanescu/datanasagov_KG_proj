# Improvements list

The changes to make to the pipeline itself: what to change, why, and where the idea came from. Not to be confused with the upkeep (`upkeep.md`): what a person running the pipeline does, and when. An item that is done is deleted here, and the commit that does it says so. Measured results that an item rests on are in [`findings.md`](findings.md).

## The whole pipeline

- **Repeat runs, to measure run-to-run noise.** A setting that skips the saved answers, so that a step can be run again with exactly the same settings. One run isn't a baseline: two runs of step 040 with the same settings, differing only by one rule of the prompt (rule 8), spelled 41 of the 63 entity classes and 67 of the 126 predicates the same. From: [`findings.md`](findings.md), 2026-10-12.

- **A batch API at NASA's LiteLLM**, if it has one: many calls sent together, at a discount. Ask NASA's LiteLLM administrators. From: 2026-10-13.
- **Keep the saved answers safe:** every model answer behind a reported number is in the steps' `cache/` folders under `outputs/`, which Git doesn't carry, so they exist only on the computer that ran the step (`previous_runs/` keeps each step's earlier output files, not its `cache/`). Archive them with each run that numbers are reported from. From: the methods review of 2026-10-11, item 7.
- **Record the first real evaluation in [`findings.md`](findings.md):** 070 run 2026-10-22_1615 evaluated a 060 run made with the real model; their numbers and tokens are in their reports on the NASA laptop, and `findings.md` has no entry for them yet. From: 2026-10-22.

- **`tests/run_all.py` on the NASA laptop:** its first run there reported that the tests changed files, and the next run passed. Find why. From: 2026-10-12.
- **README, *How to reproduce*:** setup and running are in [`running_on_nasa_laptop.md`](running_on_nasa_laptop.md); building the graph waits for step 080. From: my old to-do list.
- **Other catalogs:** some things fit only data.nasa.gov. The catalog's address is fixed in the code (`010_harvest/010_harvest_helpers/ckan_client.py`); "undefined" is treated as a maintainer (`020_clean/020_clean_helpers/maintainers.py`); splitting into strata needs a maintainer field that other catalogs may not fill; step 040's prompts say "a catalog of NASA datasets". From: the methods review of 2026-10-11, item 11.
- **Competency questions:** 10 to 20 questions the knowledge graph should answer, to judge it by. From: the literature review of 2026-10-07.
- **An entity class hierarchy for the schemas:** the ground truth schema is flat (no entity class is a kind of another). An umbrella entity class with subclasses is standard in knowledge graph schemas (subClassOf in RDF Schema); for people and groups it has a standard name, Agent, with Person, Organization and Group under it (FOAF; PROV-O). With it, a pin could say any -> Agent instead of listing Organization, Person and Team (DEVELOPED_BY_PARTY, SPONSORED_BY_PARTY), and the graph could answer questions across the kinds. It touches the schema reader and its file format, the pin check, step 040's induced schema, and step 070's translation table, so it is a design change for after the first run. Some entity classes only ever appear as the object of one predicate, and their definitions just restate it: Purpose (HAS_PURPOSE), Task (RESPONSIBLE_FOR), Role (SERVES_AS), ProcessingLevel (HAS_PROCESSING_LEVEL), SpatialRepresentation (HAS_SPATIAL_REPRESENTATION). They cause no disagreement today, unlike Value and Time, which were merged for that reason on 2026-10-20; with a hierarchy they could sit under one umbrella entity class (e.g. Label). From: 2026-10-20.

## 040_induce_schema

- **The sample of texts:** 10 maintainers × 15 texts is the documented baseline, not a design shown to be best. Taking only the 10 largest maintainers, it can never sample the records of the other 412 maintainers, which hold 8.4% of the catalog's records (040's guide, *Known limits*; the methods review of 2026-10-11, item 3). Compare designs with `helpers/compare_runs.py`, guided by the saturation curve in 040's report. From: [`findings.md`](findings.md), 2026-10-12.
- **`min_support`** above 1 (it is 1, which keeps everything found): try other values once runs can be compared. From: 040's guide, *Settings*.
- **Near-duplicate texts inflate support.** If a maintainer's 15 texts are nearly the same text, every schema entry found in them counts 15 times. Measure how alike each maintainer's texts are; then drop the near-duplicates (taking others from the same maintainer), or count that maintainer once. It matters once `min_support` is above 1. 040's report lists twins between the texts it learned from and the pool, not near-duplicates among its own texts. From: my old to-do list.
- **Nothing filters junk from stage 2:** e.g. "dataset" as a bare subject instance, or "VNP43D66 is the BSA" read as an "is a" statement, both gaining real support. A list of generic subject instances to drop would cost nothing. From: my old to-do list.
- **Alternatives to stage 4 (merging synonymous labels):** grouping by similarity, passing the chosen labels forward from batch to batch, or another approach entirely. From: my old to-do list.
- **Which text fields to learn from:** 040 uses `title` and `notes` and any field 020's `extra_text_fields` adds; which other fields help is untested. First candidate: the names of the files attached to a record (e.g. `…L3m.8D.SST4…nc`), which can say what a dataset holds when its notes describe several (2026-10-19, record #4). From: my old to-do list.
- **Ideas to compare the induced schema with:** the Purview glossary, Neo4j's capabilities, the five science domains of NASA's Science Mission Directorate (SMD) site, and the filters data.nasa.gov's search offers. From: my old to-do list.

## 070_evaluate

- **Translation that depends on the entity classes:** a row of the translation table translates a predicate one way only, whatever the entity classes of its subject and object (070's guide, *Known limits*, *One translation per component class*). Let a row translate a predicate of the current schema according to its subject's entity class, its object's entity class, or both: rows for (subject's entity class, predicate), (predicate, object's entity class), and (subject's entity class, predicate, object's entity class), besides the predicate alone as now. The most specific row that matches wins: all three over either pair, either pair over the predicate alone. When a (subject's entity class, predicate) row and a (predicate, object's entity class) row both match and disagree, 070 stops and names both rows, so a person adds the row with all three. These keys have the shape of the current schema's patterns (e.g. [Dataset, SOURCED_FROM, Mission]), so the rows can be listed from the patterns. Example: SOURCED_FROM (current schema) translates to (none) today; with rows, SOURCED_FROM with a Mission object would translate to FROM_MISSION, with a Spacecraft object to FROM_SPACECRAFT (ground truth schema), and otherwise to (none). In record 2705e0d1 (pool position 3), the extracted triple "Aquarius L3 Weekly Polar-Gridded Sea Surface Salinity V005" (Dataset) SOURCED_FROM "Aquarius/SAC-D" (Mission) is a true fact, counted extracted only; with the (SOURCED_FROM, Mission) row it would translate to FROM_MISSION, the predicate of the ground truth triple "Aquarius L3 Weekly Polar-Gridded Sea Surface Salinity V005" (Dataset) FROM_MISSION "Aquarius/Satélite de Aplicaciones Científicas (SAC-D)" (Mission). Changes 070, the translation table's format, and the annotation tool's Translation table view. From: 2026-10-24.
- **Raise With Mentors: checking a sample of the occurrences left extracted only,** to see how far precision and recall are understated ([`metrics/pairs.md`](../070_evaluate/metrics/pairs.md), *The same fact in different words*). It's an involved process: such an occurrence can be the same fact in different words as a ground truth triple left ground truth only, a repeat of a fact already paired, a fact the ground truth lacks, the result of a wrong translation, or actually wrong, and each means something different. From: 070's guide, *To do*, until 2026-10-14; now [`metrics/precision.md`](../070_evaluate/metrics/precision.md) and [`metrics/recall.md`](../070_evaluate/metrics/recall.md), row 4 of each.
- **About 10 records annotated from scratch,** with no drafted triples: measures how far drafted triples steer annotation (recall may be overstated by a model-drafted ground truth: [`metrics/recall.md`](../070_evaluate/metrics/recall.md)). From: the literature review of 2026-10-07.
- **Listing likely pairs that the wording hides:** pairing compares words, not meaning, so the same fact in other words leaves an extracted only occurrence and a ground truth only triple ([`metrics/recall.md`](../070_evaluate/metrics/recall.md#when-a-ground-truth-triple-counts-as-not-found), row 4). Step 070 could list, per record, each extracted only occurrence and ground truth only triple with the same predicate and the same subject instance or the same object instance (once evened out), e.g. "MODIS" ABOARD "Aqua" and "the imaging spectroradiometer" ABOARD "Aqua", for a person to review in the annotation tool as with partial pairs; a pair marked the same fact would then count. This parallels the component class mismatch check, which finds the same subject and object instances under different predicates. From: 2026-10-24.
- **A second annotator** for a sample of records, to measure agreement between people (Hripcsak & Rothschild 2005). From: the literature review of 2026-10-07.
- **A second person checking a sample of the translation table,** frozen before the held-out part is looked at. From: the literature review of 2026-10-07.
- **Kinds of translation, not only "means the same":** a row of the translation table now says only that a component class of the current schema means the same as one of the ground truth schema, or `(none)`. TRACE-KG, "Beyond Predefined Schemas: TRACE-KG for Context-Enriched Knowledge Graph Generation" (2026, [paper](https://arxiv.org/abs/2604.03496)) judges each pair of a ground truth schema component class and a candidate from the schema it learns: "Judgements are Equivalent, Narrower, Broader, or Unrelated", and "Equivalent counts as exact recovery and Narrower as compatible refinement". A model proposes and verifies: it takes the closest candidates for each ground truth schema component class and checks each pair with "a structured LLM verifier, with targeted human auditing of low-confidence cases" (the paper doesn't say how confidence is measured). Consider recording the kind in each row, e.g. narrower: suppose the current schema has MOUNTED_ON_SATELLITE and the ground truth schema has ABOARD; then MOUNTED_ON_SATELLITE is more specific than ABOARD, and its row would say narrower. Then decide which kinds count as within reach (narrower, probably; broader, not without more). Consider also whether a model's confidence could pick which rows a person must check, alongside *A second person checking a sample of the translation table*. A broader row is the case *Translation that depends on the entity classes* handles: SOURCED_FROM (current schema) is broader than FROM_MISSION (ground truth schema), and its object's entity class picks the narrower meaning. From: 2026-10-24.
- **Gaps in the translation table** (164 rows, commit f92cf0c), found when reviewing it: (1) the current schema (from step 040) has no predicate for FROM_MISSION or FROM_SPACECRAFT (ground truth schema), though they are common facts about a dataset, so those ground truth triples can never pair strictly and lower recall whatever extraction does. (2) HAS_OBJECTIVE and USED_TO_STUDY (current schema) both translate to HAS_PURPOSE (ground truth schema), pinned any -> Purpose, but nothing translates to Purpose; check it against step 040's patterns, which exist only in the run on the NASA laptop. - **Other quality metrics,** e.g. coverage (see *Coverage of the ground truth schema, as a second number next to the recall upper bound*). 070 already reports F1, partial pairs, entity-class accuracy, the recall upper bound, recall within reach, describes accuracy, and precision and recall per predicate and per entity class. From: my old to-do list.
- **Coverage of the ground truth schema, as a second number next to the recall upper bound:** TRACE-KG, "Beyond Predefined Schemas: TRACE-KG for Context-Enriched Knowledge Graph Generation" (2026, [paper](https://arxiv.org/abs/2604.03496)) reports coverage: the proportion of the ground truth schema's component classes that the ground truth triples use ("ontology [ground truth schema] relations [predicates] appearing in the gold [ground truth] triples together with their domain and range concepts [subject classes and object classes]") that have an equivalent counterpart in the schema it learns ("Exact"), or an equivalent or narrower one ("Compat"; its table fits that reading, its text doesn't spell it out). It weighs them by use: "Anchors [these component classes] are frequency-weighted according to scope-specific gold [ground truth] triple counts". The [recall upper bound](../070_evaluate/metrics/recall_upper_bound.md) counts ground truth triples too, so a predicate many ground truth triples use weighs more. A count with each component class once, however often the ground truth triples use it, would show how many kinds of fact the current schema lacks. Example: suppose 200 ground truth triples use 20 predicates, 2 of them in 1 ground truth triple each, and no checked row translates to those 2. Then the recall upper bound is 198/200 = 99%, while 18 of the 20 predicates (90%) are within reach. Report the count per predicate and per entity class; if narrower rows count (see *Kinds of translation, not only "means the same"*), it counts them too. From: 2026-10-24.

## 080_build_graph

- **Before designing 080, read the rest of** Negro, Futia, Kůs, and Montagna, *Knowledge Graphs and LLMs in Action* (Manning, 2026): chapter 3 (RDF or a labeled property graph), chapter 4 (combining several sources: phase 1's graph and phase 2's triples), and chapters 13 and 14 (how people ask questions of a finished graph, for the competency questions). Chapters 5 to 8 and part of 14 were read on 2026-10-14 (the items here citing the book). From: 2026-10-14.
- **Three layers:** the records; each extracted triple as extracted (never joined with another), with its record and source text; and the knowledge graph built from those. The knowledge graph can then be rebuilt without asking a model again, and every edge can show the passage it came from. From: Negro, Futia, Kůs, and Montagna, *Knowledge Graphs and LLMs in Action* (Manning, 2026), section 6.1.
- **A layer of facts from the model's own knowledge:** joining names ("MODIS" = "Moderate-resolution Imaging Spectroradiometer (MODIS)"), reading codes ("MID-IR" in a title meaning SST4), and background facts, each marked as the model's, kept apart from the extracted triples (which stay what the record states), and checked by a person on a sample, with its own accuracy. From: 2026-10-19.
- **A record's node: `Dataset` or `CatalogEntry`?** Phase 1's graph makes each record a node labeled `Dataset`, while the describes triple gives the record the entity class `CatalogEntry` and gives `Dataset` (or `WebTool`, …) to what its title names. Decide which the graph uses before building it. From: the terminology sweep of 2026-10-15.
- **Linking subject instances and object instances to reference lists,** so that one thing named several ways ("Aqua", "EOS PM-1") becomes one node. First processing levels, a short fixed list (L0, L1A, L1B, L2, L3, L4: every spelling, such as "Level 3" or "L-3", mapped to one); then NASA's missions ([A to Z of NASA missions](https://www.nasa.gov/a-to-z-of-nasa-missions/)), where a subject or object instance with no match is marked for a person to check, not dropped, since the catalog also names missions of other agencies; GCMD keywords as another list. How: the subject or object instance keeps the record's words and gets an edge to its entry, saying how the match was made; candidates come from the list, never from a model (exact match after evening out, "Long Name (ACRONYM)" split into both forms, then near spellings as candidates only); a model chooses only among two or more candidates, and may answer "none of these"; a small hand-checked set of subject or object instance → entry (or none) measures it. Aliases ("EOS PM-1" for Aqua) must be written for our lists. From: my old to-do list; 2026-10-13; Negro, Futia, Kůs, and Montagna, *Knowledge Graphs and LLMs in Action* (Manning, 2026), chapters 7 and 8 (which choose without a "none" answer and don't measure linking).
- **Which predicates give properties instead of edges,** by the rule of README, *Phase 1*: a processing level, for example, has few values, which people filter by but don't go from node to node through. From: my old to-do list; 2026-10-13.
- **Splitting a number with a unit** ("250 m") into a value and a unit, as graphs store quantities (Wikidata, QUDT, schema.org's QuantitativeValue). From: 2026-10-11.
- **One written form for every value:** every exported value is written in one form, whatever spelling the record used: a number, a space, and the unit, as the SI brochure prescribes (e.g. 500 m, never 500m; 4.63 km; the only exceptions are °, ′ and ″ of a plane angle, written with no space). Matching (070, the annotation tool) already treats both spellings as the same; the graph must not keep both. From: 2026-10-20; BIPM, *The International System of Units (SI)*, 9th edition (2019), section 5.4.3.
- **A fact many records state:** one edge per extracted triple, or one edge listing the records it came from. Either way, keep which records each edge came from. From: 2026-10-06.
- **Joining subject instances and object instances that name the same thing into one node** beyond the lists: similar spelling plus shared neighbors (two spacecraft names spelled alike that carry the same instrument), grouped into connected components, the longest name kept; generic words ("Data", "Product", "Level") never count as similar. Which subject instances and object instances to join across records, and which to keep as one node per record: specific named things join (one MODIS node, one Aqua, one NASA), since they are important and specific. Generic descriptions don't: "L2 pixels" (record #4, pool position 4), "radiance data" and "a series of screens" (pool position 2) each mean that record's own data or method, so one shared "L2 pixels" node would wrongly connect unrelated datasets. Matching words alone can't tell the two kinds apart, so 080 needs a test for it: e.g. a proper name or an acronym against a common noun phrase, or a model's judgment checked on a sample. Organizations inside organizations: the ground truth keeps an organization's name whole, as written (e.g. "NASA Ocean Biology Processing Group (OBPG)", pool position 4), because "NASA" there says whose group it is, while in "NASA Technical Standards Program" (pool position 0) it is part of the name, and wording alone can't tell the two apart. So 080 should add part-of edges (OBPG part of NASA) from a known list of NASA's organizations, not from the words, so that such groups connect to the one NASA node. Groups named with a person: rule 12 of the annotation guidelines keeps "Peter Minnett and his team" (pool position 4) whole as one instance, because "his team" alone isn't complete. So that node won't join a "Peter Minnett" node from another record; 080 should link the two (the team includes the person) rather than leave them unconnected. Same name, different things: NASA often gives a mission and its spacecraft the same name (Dawn, Rosetta, Aqua). A Mission node and a Spacecraft node with the same name must stay two nodes, never joined because the names match. They may be linked (the spacecraft belongs to the mission), but only from a record that states it.
